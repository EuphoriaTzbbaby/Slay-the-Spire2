## Slide 3｜游戏介绍：什么是《杀戮尖塔 2》

**页面标题**

## 一款“卡牌构筑 + Roguelike”的策略游戏

**页面要点**

- 《杀戮尖塔 2》（Slay the Spire 2）是 Mega Crit 的卡牌构筑 Roguelike 续作
- 核心循环：选角色 → 走地图 → 战斗 → 选牌/遗物/药水 → 构筑牌组 → 打 Boss
- 战斗资源：能量、手牌、抽牌堆、弃牌堆、格挡、能力、敌人意图
- 决策空间大：出牌顺序、目标选择、是否结束回合、拿牌/跳过、路线风险
- 已有 co-op 形态：多名玩家各自控制角色，共享一局 run

**讲稿**

StS2 的乐趣不只是“打出高伤害”，而是每一层都在做资源交换：这回合要不要贪伤害、这张牌要不要拿、这条路要不要打精英。它的决策空间很大，而且信息不完全——抽牌顺序、未来敌人、随机事件都不是完全可见的。这正是 AI 很难“真正玩好”的原因。

## Slide 5｜需求定义：我们到底要做什么

**页面标题**

## 一个“懂游戏、能做事、像队友”的 AI

**页面要点**

1. **看得懂**：知道手牌、牌组、遗物、药水、敌人意图、路线、奖励
2. **打得对**：基于当前状态给抓牌/打牌建议，动作合法、有理由
3. **说人话**：提供情绪价值，能吐槽、鼓励、复盘，最好有语音
4. **能做事**：自动帮玩家打牌；进一步，AI 控制第二个角色，和玩家双排

**讲稿**

我们的目标可以概括成四句话：看得懂、打得对、说人话、能做事。前两个是“参谋”，第三个是“搭子”，第四个是“队友”。这也是我们和普通 LLM 聊天框最大的区别。

## Slide 6｜研究现状：三条路线

**讲稿**

我们调研了三个最接近的项目。它们各自都很强，但拼在一起才能覆盖我们的需求：Spire Buddy 有陪伴感，STS2-Agent 有双人身体，CombatSolver 有强战术。我们的工作不是重复它们，而是把三者的优点组合起来，并补上“语音 + 情绪价值 + 双排”的空白。

## Slide 7｜Spire Buddy：最接近“游戏内 AI 搭子”

**页面标题**

## Spire Buddy：自包含的游戏内 AI 助手

**页面要点**

- 形态：C# Mod，进程内运行，无需外部服务
- 能力：Chat / Settings / 人格 / 自动游玩 / Jev / CombatSolver 集成
- 技术：OpenAI-compatible、动作枚举与校验、ILSpy 进程内查规则
- 优点：安装简单、游戏内体验完整、MIT 许可
- 不足（用户体感）：
  - 复杂战斗下策略深度有限，**“有点蠢、不太会打牌”**
  - 多轮模型调用导致**反应较慢**
  - **缺少语音陪伴**
  - 不是双人 co-op 的 AI 队友

**配图建议**

**讲稿**

Spire Buddy 是我们最直接的对标。它已经证明“游戏内 AI 搭子”是可行的，而且体验不差。但它的战斗仍然依赖 LLM/Jev；在没有接 CombatSolver 的复杂局面里，用户会觉得它不够强、反应慢，而且只能打字，没有语音陪伴。

## Slide 8｜STS2-Agent：最接近“AI 双排”

**页面标题**

## STS2-Agent：把 AI 变成第二个玩家

**页面要点**

- 形态：C# Mod + 双实例 co-op + 本地 HTTP API/MCP
- 能力：
  - 本地拉起第二个游戏实例
  - AI 控制第二个角色
  - 团队聊天、主动短评、地图投票
  - 外部 Agent 接管
- 优点：真正解决“双人身体”和“可编程接口”
- 不足（实测）：
  - 与部分 Mod 兼容性差，多人要求 Mod 一致
  - **DeepSeek API / tool calling 实测未打通**
  - macOS 中文 UI 出现字体缺失
  - 配置链路长，普通玩家上手成本高

**配图建议**

**讲稿**

STS2-Agent 解决了最难的一件事：AI 真的能作为第二个玩家进入 co-op。但它是“工程底座”，不是“产品”。Mod 冲突、模型兼容、macOS 字体、配置复杂度，都会拦住普通玩家。这正好是我们的机会：做一层更友好、更聪明的上层。

---

## Slide 9｜CombatSolver：战斗很强，但太慢

**页面标题**

## CombatSolver：预算内搜索的“战斗专家”

**页面要点**

- 形态：StS2 战斗路线求解器 Mod
- 能力：跨回合模拟、预算 beam、路线展示、自动执行
- 优点：战斗战术强度高，能给出整场战损
- 不足：
  - 搜索预算大，**响应慢**
  - “最优路线”来自大规模搜索/beam，**交互性弱**
  - 没有情绪价值、语音、双排
  - 对普通玩家来说，等待成本高

**讲稿**

CombatSolver 证明了一件事：战斗要强，必须靠搜索/模拟，不能靠 LLM 拍脑袋。但它也暴露了另一个问题：强搜索很慢。我们的思路不是放弃搜索，而是把搜索放在合适的层级：当前回合用快速 exact/beam，长程用预算 rollout，LLM 只负责表达。

## Slide 10｜研究空白与我们的定位

**页面标题**

## 空白：没有人把“强战术 + 情绪价值 + 语音 + 双排”合在一起

**页面要点**

```text
Spire Buddy      = 陪伴 + 自动打，但战术/语音/双排不足
STS2-Agent       = 双排 + API，但模型兼容/配置/表达不足
CombatSolver     = 强战术，但慢、无陪伴、无双排
我们的目标       = 战术脑 + 表达脑 + 双人身体
```

**页面要点 2**

- 不是“再做一个 solver”
- 不是“再做一个聊天框”
- 是 **AI 双排搭子**：能打、能说、能陪、能协作

**讲稿**

这三个项目各缺一块。Spire Buddy 缺强战术和双排，STS2-Agent 缺表达和易用性，CombatSolver 缺陪伴和协作。我们的定位就是把三者交叉起来：用 solver 保证不蠢，用 LLM 保证像人，用 co-op 保证能一起玩。

## Slide 11｜我们的方案：混合架构

**页面标题**

- **表达脑**：LLM 负责人格、吐槽、复盘、语音
- **安全层**：合法动作校验、快照新鲜度、预算、暂停/接管

**配图建议**

- `assets/ppt/architecture.png` 全图

**讲稿**

我们的架构可以概括为“三个脑 + 一个身体”。身体负责进入游戏、读状态、执行动作；战术脑负责算；表达脑负责说；安全层保证 AI 不会乱点。这样既不会让 LLM 做它不擅长的算术，也不会让搜索系统不会说话。

## Slide 12｜功能一：基于当前状态的抓牌/打牌建议

**页面标题**

## 不是“泛泛攻略”，而是“这一回合、这一手牌”

**页面要点**

- 输入：手牌、能量、牌堆、遗物、药水、敌人意图、当前 Act/HP
- 输出：
  - 推荐动作 + 手牌索引 + 目标
  - 预计掉血 / 敌方剩余 HP / 是否击杀
  - 备选 top-3 + 理由
- 抓牌建议：
  - top-1 / top-3 / skip
  - 依据：卡牌强度、牌组协同、费用曲线、当前 Boss/路线
- 关键：**LLM 只解释，不直接算数值**

**配图建议**

- 左侧：`game-combat.jpg`
- 右侧：一个“推荐卡片”UI 草图：
  ```text
  推荐：防御 [0]
  预计：掉血 7，敌方剩 31
  备选：打击 [1] / 痛击 [2]
  ```

**讲稿**

第一项功能是“当场参谋”。它不是给一张静态 tier list，而是根据你现在的手牌、能量、敌人意图，算出这回合怎么打、掉多少血、能不能杀。抓牌也一样：结合牌组和路线，而不是只看单卡评分。

## Slide 13｜功能二：情绪价值与语音陪伴

**页面标题**

## 像队友，而不是像攻略网站

**页面要点**

- 人格：名字、语气、口头禅、吐槽等级、边界
- 触发：战斗开始/结束、关键抽牌、危险回合、选牌/商店、玩家主动问
- 表达：
  - 先给信息，再给情绪
  - 吐槽决策，不攻击人
  - 不刷屏，可静音，可仅字幕
- 语音：TTS，先字幕后语音；首包延迟目标 < 2 秒
- 技术：LLM 生成台词 + 规则控制频率 + TTS 播放队列

**配图建议**

- `assets/ppt/game-commentary.jpg`（AI 解说画面）
- 右侧放一个“语音气泡”示意

**讲稿**

第二项是情绪价值。我们希望 AI 不是冷冰冰地报数字，而是会说“这波不亏”“你先别急，我挡”。但吐槽要有边界：吐槽决策，不攻击人；关键节点说，不刷屏。语音先做字幕版，再逐步上 TTS，避免一上来被延迟和音色问题拖死。

## Slide 14｜功能三：自动帮玩家打牌

**页面标题**

## 自动打，但不是“乱打”

**页面要点**

## Slide 16｜关键技术：为什么能“不蠢”

**页面标题**

## 三层防呆：搜索、校验、回退

**页面要点**

1. **搜索层**
   - 当前回合：exact 穷举（模型内最优）
   - 快速近似：beam
   - 长程：2–3 回合 rollout
   - 强基线：CombatSolver（可选/离线评估）
2. **校验层**
   - 本地枚举合法动作
   - 快照新鲜度检查
   - 非法索引拒绝 + 返回合法索引
3. **回退层**
   - 搜索超时 → beam
   - 模型失败 → 规则/本地策略
   - 连续失败 → 停止并解释

**配图建议**

**讲稿**

“不蠢”不是靠更大的模型，而是靠三层防呆：搜索负责算，校验负责不出错，回退负责不卡死。LLM 不直接决定数值，它只负责把结果说清楚。这样即使模型很弱，系统也不会乱打。

## Slide 23｜风险与应对

**页面标题**

## 最大的风险不是算法，是集成

**页面要点**

| 风险 | 影响 | 应对 |
|---|---|---|
| Mod/游戏版本不兼容 | 功能失效 | 锁版本；启动自检；降级观战模式 |
| macOS 双开不稳定 | AI 队友不可用 | 先做观战搭子；必要时 Windows 验证 |
| DeepSeek/工具调用不通 | 自动游玩失败 | 换模型；Chat/Play 分离；本地模型兜底 |
| TTS 延迟/音色 | 体验差 | 先字幕；按句合成；可静音 |
| 存档损坏 | 严重后果 | 隔离 profile；备份；不自动读档 |
| LLM 幻觉/乱打 | 不信任 | 合法动作校验；solver 决策；回退 |
| 范围过大 | 延期 | A→B→C 分阶段；Gate 验收 |

**配图建议**

- 风险矩阵：概率 × 影响，四象限
- 用红色标出“存档/兼容性”

**讲稿**

# 附录 A｜可能被问到的问题（答辩准备）

## Q1：你们和 Spire Buddy 有什么区别？

- Spire Buddy 是单实例游戏内助手，强在 Chat/人格/自动游玩；
- 我们复用它的交互思路，但增加：
  - 强战术 solver 的显式对比（exact/beam/rollout）
  - 语音陪伴
  - AI 第二大角色 co-op
  - 模型兼容层（DeepSeek/本地模型）
- 一句话：Spire Buddy 是“搭子”，我们要做“能双排的搭子”。

## Q2：为什么不用 CombatSolver 直接做？

- CombatSolver 强在战斗搜索，但：
  - 预算大、响应慢；
  - 没有情绪价值/语音/双排；
  - 不适合作为实时交互的唯一决策器。
- 我们的做法：
  - 当前回合快速 exact/beam；
  - 长程用 rollout；
  - CombatSolver 作为强基线/教师，而不是唯一在线决策器。

## Q3：怎么保证 AI 不乱打？

- 只从本地枚举的合法动作里选；
- 执行前校验快照新鲜度；
- 非法索引拒绝并返回合法索引；
- 连续失败熔断；
- 所有动作可暂停/接管；
- LLM 不直接操作游戏对象。

## Q4：12 周做得完吗？

- 分阶段：
  - 1–2 周观战搭子；
  - 2–3 周战术/选牌；
  - 2 周人格/语音；
  - 3–5 周 AI 队友；
  - 2 周评估/答辩。
- 如果 co-op 受阻，至少交付观战搭子 + 战术建议 + 语音。
- 不承诺高进阶“比人强”，只承诺可演示、可评估。

## Q5：Mod/版权/存档安全怎么处理？

- 只复用开源项目的接口/思路，不复制游戏资源；
- 注意 MIT/AGPL 许可证；
- 使用隔离 profile/存档备份；
- 不自动读档、不写玩家真实存档；
- 语音克隆需本人授权；
- 明确标注 AI 身份。
