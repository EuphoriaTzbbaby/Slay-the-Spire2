# 语音组对接：任务、测试与交付

更新：2026-11-09。面向语音组的当前工作说明。协议字段以[主 API](语音模块-开发功能与API.md)为准，开发入口见[voice/README.md](../voice/README.md)。本次更新不改变协议或已实现的接口。

## 1. 目前做到哪一步

| 能力 | 当前证据 | 尚不能据此认定 |
| --- | --- | --- |
| 真人语音 → 游戏文字 → AI 文字回复 | 负责人于 11-03/11-04 确认基础链路可用，实际游戏日志有输入 | 识别率、长句、噪声、复杂打断全部达标 |
| 基础 TTS | 11-08 负责人确认系统测试音能听到，随后确认游戏中的 AI 已能说话 | Windows 音频、所有设备、音质、延迟及全双工通过 |
| QQ 与麦克风按钮 | 已接按需启动、持续监听、关闭、托管进程回收；重启默认关闭 | 所有权限、崩溃、热插拔、反复开关场景均已实测 |
| 协议与客户端 | 已有 Python/C# 自动回归和 GitHub Actions | 自动检查能代替真人音频或 Windows 玩家安装验收 |

**现在是在已有 `voice/` 服务上完善体验和交付，不要重新做一套语音/AI 工程。** 游戏负责人暂时只验收一句话输入和 AI 基础语音回复，其余专项测试由语音组负责组织，不再要求负责人重复跑完整测试表。

当前实际行为：

- 重启游戏后麦克风和播报都关闭；QQ/麦克风按钮从关闭状态开启时默认“语音→语音（保留文字）”。输入专项测试先在“设置 → 交流方式”选择“语音→文字”，再 QQ 开启。
- QQ 是持续会话开关，每句话不需要重复按键或唤醒。再次 QQ、麦克风按钮或窗口“关闭”停止语音；“收起”及 F9 只隐藏面板，语音继续。
- **基础播报是半双工**：播报时屏蔽麦克风，丢弃播放期间音频，结束后恢复。不能把“AI 正在生成时补充”与“AI 正在朗读时插话”当成同一能力；后者当前不支持。
- 当前默认 Vosk 小中文模型、WebRTC VAD、系统中文 TTS。句尾非人声窗口约 0.9 秒，连续长句约 20 秒分段；这是现有代码参数，不是响应时间承诺，也不是已开放的 CLI 调参接口。

## 2. 语音组接下来做什么

| 编号/优先级 | 工作包 | 要交什么 | 怎么算完成 |
| --- | --- | --- | --- |
| V1 / P0 | 中文 ASR 与游戏词汇 | 改善短句、抓牌问法、牌名/遗物名、数字和否定词；提交改动、模型/参数说明及前后对照 | 用同一语料、设备和环境对照；逐句给原话/最终转写，统计 CER、语义正确率、关键槽位错误，不能只挑成功例子 |
| V2 / P0 | VAD 与切句 | 优化短停顿合句、长句收束、开头/尾字、纯噪声不提交；提供可观察采集/VAD/ASR 的诊断 | 完成下表 T02–T05；采集峰值、人声判定和识别文字分别记录；独立电平诊断目前仍是缺口 |
| V3 / P0 | 会话、取消与异常恢复 | 多次 QQ、准备中取消、断线/重连、服务崩溃、退出回收、ID 去重、过期输入清理 | T06–T10 不重放旧句、不重复控制、不在关闭后收音；能从日志定位权限/设备/模型/协议问题 |
| V4 / P0 | 基础 TTS 稳定性 | 保留并验证 enqueue/clear/cancel/TTL/终止事件；失败明确提示；播放后恢复新一轮收音 | T11–T13 耳机和外放分别实测；不把自己的声音转写成玩家输入；文本不擅自改写牌名、结论和数值 |
| V5 / P1（正式交付必做） | Windows 运行时与玩家包 | `spire-voice.exe`、同平台依赖、模型、版本/校验信息、安装/排障说明 | T14 在未安装系统 Python、没有源码/虚拟环境的干净 Windows 环境通过；安装后日常只用 QQ，不开终端 |
| V6 / P1 | 设备、权限与诊断 | 指定/默认设备、拒绝授权、拔掉设备/重新连接、缺模型的可理解反馈；提出设备切换方案 | T01/T10/T15；不以绿色图标或 PortAudio 启动成功代替真人输入。新设备/设置 API 必须与游戏组一起实现和回归 |
| V7 / P2 | 完整双向语音增强 | 回声消除、边播边听/语音打断、专用唤醒词、音色/语速设置 | 单独提出方案与验收用例；不将基础半双工冒充全双工，不阻塞本期基础交付 |

建议两人认领：一人主负责 V1/V2/V6，另一人主负责 V3/V4/V5；共同做交叉设备、Windows 和游戏集成测试。具体姓名由组内确认。每个工作包要有一个负责人、一个复测人，不代替组内实际认领。

V1 可评估词表、识别模型或归一化，但不能靠“把任何相似词都替换成某张牌”掩盖错误，也不能把游戏模型 API Key 交给语音服务。动态词表目前不是既有协议方法；需要时另提兼容设计，同步代码、协议示例和游戏端。

## 3. 哪些问题归谁

| 现象/证据 | 主要责任 |
| --- | --- |
| 玩家说“只说答案”，最终转写成“自说答案”；牌名、数量、否定词听错 | 语音组：ASR/切句；保留失败样例 |
| 转写正确，但游戏读到的候选不对、模型把“惊逃”说成别的牌、旧界面答案被显示 | 游戏负责人：快照、回答校验、过期回复处理 |
| 游戏显示文字正确，提交播报后无声、读错/漏字、恢复收音失败 | 语音组先查 TTS/设备/队列；游戏组核对是否发送及是否取消 |
| 把“先别暂停”识别成“暂停” | 语音组先查转写；转写保留否定但仍执行暂停，则查 intent 匹配与游戏复核 |
| “帮我点这张”是否授权点击、求解器是否占用、动作是否成功 | 游戏负责人；语音端不能直接操作游戏 |
| 推荐哪张更强、角色构筑与求解器算法 | 策略同学；语音组不修改这些内容 |

排障沿同一句的“玩家原话 → `input.final.text` → 游戏当前快照 → AI 文字 → `speech.enqueue.text` → 实际音频”核对，记录第一个开始不一致的位置。`input.ack accepted` 只表示输入被接收，不是 AI 已回答或游戏动作成功。

## 4. 开始测试前

### 4.1 开发环境与独立诊断

在仓库根目录准备 Python 3.11+、.NET 9；Windows 建议 Python x64。以下 Windows 示例使用 `python`，macOS 可改为 `python3`：

```powershell
python scripts/voice_dev.py setup
python scripts/voice_dev.py devices
python scripts/voice_dev.py test-mic
python scripts/voice_dev.py test-mic --input-device 0
python scripts/voice_dev.py test-tts
```

设备编号按 `devices` 的实际结果替换。`test-mic` 依赖 ASR 模型，只测一句、模型准备后最多等待约 15 秒，不是持续会话，也不是独立电平仪；`test-tts` 只测扬声器/TTS，不测 ASR。真人开口并确认可闻，分别记录输入与输出结果，不保存默认录音、不自动调整系统音量。

语音组需要独立调服务时可用 `python scripts/voice_dev.py run`；不要和游戏自启的服务抢占同一个端口。独立终端成功不等于游戏自动启动路径成功。

### 4.2 无音频自动检查

PowerShell：

```powershell
python scripts/check_repository.py
python scripts/game_dev.py check
$env:SPIRE_VOICE_WIRE_CHECK = '1'
python scripts/voice_dev.py check
```

macOS/Linux shell：

```bash
python3 scripts/check_repository.py
python3 scripts/game_dev.py check
SPIRE_VOICE_WIRE_CHECK=1 python3 scripts/voice_dev.py check
```

先运行游戏检查以构建跨语言检查程序。以上不要求启动真实游戏、不访问真人麦克风；mock 也只能证明协议与路由，不能填为真人 ASR/TTS 通过。新增依赖同步 CI，并检查所交提交的 Actions 结果。

### 4.3 游戏自动启动路径

开发机先按[游戏 README](../game/legacy/README.md)构建、安装，再重启游戏；C# 修改必须重启，Python 改动也应重启由游戏托管的服务，不能一直复用旧手动进程。测试时不预先运行 `voice_dev.py run`，由 QQ 自动启动。

macOS 必须通过独立「尖塔语音 / Spire Voice」的正常麦克风授权验收，不能用终端权限代替。Windows 另查系统麦克风隐私权限与中文系统音色。玩家安装包验收用 V5 的运行时包，不使用开发机 `voice-launch.json` 或源码虚拟环境。

## 5. 真人与游戏测试表

以下每行分别填“通过/失败/未测”、实际次数、证据和缺陷号。默认先在测试跑局或只读建议场景进行，避免诊断语句误触真实购买/选牌；要测动作时由游戏负责人确认测试场景。没有明确阈值的项先记录实测分布，再由两组确认门槛。

| 编号 | 步骤与建议次数 | 预期/必须记录 |
| --- | --- | --- |
| T01 权限/设备 | 默认麦克风与指定设备各说 5 句；分别测试拒权限、缺模型、无输入设备 | 真实采样/VAD/最终文字分别可见；错误有原因，不能只显示“已开启”。有局限就写未测/不支持 |
| T02 安静/噪声 | 安静 60 秒；键盘、鼠标、游戏音效各 60 秒 | 统计误触发 VAD、误提交 final、空输入；无声不退出持续模式，非零峰值不冒充人声 |
| T03 短停顿 | “我想……”停约 0.3/0.5 秒接“先防御”，各 5 次；完整句结束后停约 2 秒 | 短停顿尽量合成一条，完整句只提交一次；记录首/尾字丢失、拆句/粘句次数与 final 延迟 |
| T04 长句 | 约 10 秒与 25 秒连续说话，各 3 次，再接一句短句 | 不无限等待或堆积音频；长句按上限分段，下一句不带上旧文本；记录分段位置和顺序 |
| T05 普通话/术语 | 按第 6 节固定语料做基线和优化后对照 | 记录原话、partial、final、CER、语义/关键槽位；不能拿 AI 猜对意思代替转写正确 |
| T06 开关与重启 | QQ 连续开关 10 次，每次说一句；准备中 QQ 取消 3 次；重启游戏 3 次 | 一次操作只切一次状态；关闭后说话 10 秒无新输入/播报；重启默认为关，旧草稿不提交 |
| T07 模式/面板 | 文字→文字、语音→文字、语音→语音各 3 轮；另测收起/F9/窗口关闭 | 文字模式不启动麦克风与播报；语音→文字不自动读出；语音→语音保留文字并播报；收起不关语音，关闭则停；切模式不重复提问 |
| T08 生成中补充 | AI 尚在生成时说“等等，简单回答就行”，5 次 | 临时文本不新建 AI 请求；final 后由游戏合并原问题和补充，取消旧回复；记录乱序、旧回复覆盖和请求次数。此项由游戏组一起复测 |
| T09 协议/重连 | 同一个 `(session_id,input_id)` 重发；断线、重连、服务退出各 3 次 | 一次最终输入不重复聊天/动作；断线清理，重连只收新句；新会话不沿用旧请求/输入/播放队列 |
| T10 故障/退出 | 识别中 QQ 关闭；播放中 QQ 关闭；退出游戏；在测试会话让自启服务崩溃后重开 | 立即停止接收新输入，未提交句不漏出；自启进程按生命周期回收，手动进程不被误杀；记录是否需手工干预 |
| T11 TTS 可闻性 | 10 条短回复，含中文、牌名、数字；耳机和外放分别测试 | AI 文字、enqueue 文本与实际读音逐条比对；记录漏读/重复/失败；进程退出码 0、speech.started 都不等于使用者听到了首音 |
| T12 半双工/回声 | AI 播报期间说话；播报结束后立刻说“下一句测试”，各 5 次；两种输出设备分别测 | 当前播放期间这段话不会提交，这是已知半双工边界；AI 自己的声音不变成玩家输入；播放结束后的新句能恢复识别，检查恢复后首字和尾部回声 |
| T13 取消/失败 | 播放中点停止播报、QQ 关闭；排队取消、TTL、合成失败分别检查 | 每条播报有 completed/cancelled/error 终态，不继续读旧条目；错误不会卡住下一句。UI/真实声音与协议检查分别记录 |
| T14 Windows 玩家包 | 干净 Windows 环境解压运行、首次授权、QQ 说话与播报、关闭和重启 | 不安装系统 Python、不引用源码路径，不开终端；模型/依赖齐全，QQ 闭环和退出回收可复现；缺组件时有明确提示 |
| T15 换设备 | 有线/USB/蓝牙设备按可用条件测试断开、重连、系统默认设备改变 | 记录设备和采样率，说明是否需 QQ 重开；运行中设备选择 API 尚未实现，不能按文档假设存在 |

交付阻断条件：关闭后无新采集/输入；未鉴权不得采集；重复输入不得重复触发游戏动作；未提交草稿不执行口令。发现这些问题先阻断交付。生成中补充、复杂设备和噪声测试由语音组承担，负责人只做修复后的重点复测。

## 6. 固定语料与量化记录

先准备 **30 句**：15 句普通会话/自然停顿、10 句游戏术语与数字、5 句固定口令/否定问句。至少 2 人，在安静和正常游戏音效两种环境各读一次，共 **120 次输入尝试**；失败、超时、空输出也计入总数。优化后使用同一语料/硬件条件复测，不靠大声重读或替换失败句提高分数。

口令的具体 intent 按主 API 的完整匹配约定核对；否定/问句不应被截成控制事件。这些句子用于测试输入，不能据此宣称对应游戏动作或模式切换已执行；测试控制/动作必须在第 5 节约定的测试场景完成。

已有失败样例可作回归：玩家“只说答案”曾出现“自说答案”；“推荐抓哪一个”出现漏词。这些是识别质量问题，不通过 AI 回答碰巧合理来标记成功；也不要把“慎选”全局硬替换成“惊逃”。

记录指标：

- CER = 编辑距离 / 参考文本字符数；注明去空格/标点等统一规则，原始转写仍保留。可汇总总编辑距离/总参考字符数；漏句计删除，超时/空结果不排除。
- 另报整句语义正确率、牌名准确率、数字/否定词错误数、拆句/粘句数、每分钟噪声误提交数、重复 final 数。语义判定规则先定下来，由另一人复核。
- 以统一测试时钟记录：开始发声→VAD；最后一个字结束→final；final→游戏接收；游戏接收→AI 文字；AI 文字→实际首音；播放结束→恢复收音。用 session/input/utterance ID 关联。不同进程的未校准时钟不能直接相减。
- 给样本数、P50/P95 与失败数，不只写平均值。冷启动/热启动、模型耗时、AI 服务耗时与 TTS 耗时分开，0.9 秒句尾窗口不能被写成 0.9 秒必达总延迟。

目前没有已经双方验收通过的统一“识别率 ≥ 某数/延迟 <2 秒”承诺。语音组先交基线与候选目标，再与游戏组确认；第 5 节的交付阻断条件和不伪报成功不等待阈值协商。

## 8. 协议与已知边界

- 保留现有 v1 信封、token 鉴权、session/input/request 去重和心跳。持续模式的 `recognition.started/partial`、`recognition.cancelled/timeout` 与 `input.final` 仍按主 API，不新建一套控制事件；partial 只显示/触发生成中取消，不提交聊天或执行动作。
- 本期完整服务包含 `speech.enqueue` 与对应播放/取消事件。只提供 ASR 的独立测试服务必须手动使用“语音→文字”，不能让 QQ 默认输出模式调用一个假装支持 TTS 的服务；游戏端能力控件门控仍是对接待办。
- 当前 `devices.list/select`、`settings.update`、`service.shutdown` 不是已实现的服务请求。CLI `--input-device` 不等于运行中设备切换 API；新请求与 ready/loading 流程必须同步两端。
- 当前 `settings.get` 的说明文字仍写着游戏默认文字回复，是待修的小项，不应用它判断游戏当前模式；实际行为以模式设置和请求为准。
- 唤醒词专用检测、音色设置、真 AEC、边播边听、主动发言/自动决策的播报挂点另行交付。基础 FIFO/取消等已有代码与协议检查，接下来验收真实使用表现，不从零重复造轮子。
