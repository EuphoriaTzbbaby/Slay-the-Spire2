# 语音组对接：交付范围、任务与验收

更新：2026-11-03。依据项目负责人最新范围：**当前只要求玩家语音输入，AI 保持文字回复，先确认能检测到玩家发声。** 完整消息契约见[语音模块开发功能与 API](语音模块-开发功能与API.md)，运行现有代码见[voice/README.md](../voice/README.md)。

## 1. 可以直接给语音组的任务说明

请在现有 `voice/` Python 服务上迭代，先交付“能收到麦克风音频，并能看见玩家说话开始/结束”的独立诊断；再把中文识别结果按 `input.final` 发给游戏。游戏端复用现有 AI 聊天并显示文字。当前不用先把 AI 声音做出来，不以 TTS、音色、播报队列或唤醒词阻塞输入验收。

语音组负责音频采集、权限/设备、发声检测、句末切分、ASR、语音服务与异常处理；游戏负责人负责模型、快照、聊天/字幕、交互界面和游戏动作权限；另外两位策略同学继续负责策略优化。两位语音成员如何认领下表由组内确定，原文档逐项指定马/胡/付的安排不视为当前分工确认。

## 3. 语音组本期工作包

| 编号 | 工作包 | 必须交付 | 当前代码基础/缺口 |
| --- | --- | --- | --- |
| I1 | 设备与权限 | 列出输入设备，选择默认/指定麦克风；权限拒绝、设备不存在/断开时有明确反馈 | 已有 CLI 枚举与 `--input-device`；运行中切换、权限细分仍需完善 |
| I2 | 采集与发声检测（A0） | 不依赖 AI 回复/扬声器；提供持续可观察的电平、说话开始/结束和无声反馈，区分底噪与发声 | 当前 `test-mic` 依赖 ASR 模型，只在识别成功或 15 秒超时结束；峰值不是 VAD，需补独立诊断/人声活动能力 |
| I3 | 中文识别与切句（A1） | QQ 开启后连续识别，每句停顿输出一次最终文字；支持无声、取消、超时和识别失败 | 已有 Vosk 原型；2026-11-03 用户已确认真人转写进入游戏，准确率和游戏专有词汇仍需建立样本与错误记录 |
| I4 | 本机服务与兼容 | 完成鉴权、心跳、状态、输入事件、回执；中文传输、重复输入、断线清理稳定 | 已有 Python 服务与 C# 客户端；按主 API 的最小兼容集对接，不重新设计一套不兼容协议 |
| I5 | 固定口令 | 完整匹配暂停/恢复/到你了；否定句、问句不按关键词误触发；只发一次最终事件 | 已有匹配函数和自动检查；实际识别效果与真实游戏回执待测 |
| I6 | 可复现交付 | 源码、依赖/版本、模型获取方式、启动与设备选择说明、测试报告；玩家版含独立运行时、模型与依赖，QQ 全程控制 | 已有按需自启与进程回收、开发机安装配置、`--voice-runtime` 纳入安装包；语音组仍需交付 Windows 可执行目录并实机验收，不能要求玩家开终端 |

I1/I2 是当前第一交付。I3/I4 组成“语音→文字”闭环。I5 不得靠识别服务直接执行游戏动作。A0 不要求做声纹或识别具体是谁，只需对实际设备上的说话活动给出可信反馈。

两人拆分建议：一人侧重 I1–I3 的采集、发声和识别，另一人侧重 I4/I6 的服务、错误、复现与交付；I5 和实机联调共同完成。这是建议分工，具体名字待组内认领。

## 4. 与现有游戏端对接时容易漏掉的约定

1. Python 监听 `127.0.0.1:17860`，游戏作为客户端；token 由游戏生成，语音端读取游戏写出的会话文件，不各自生成两个令牌。
2. 游戏准备连接不等于采集；QQ 开启时在握手/状态查询后发 `listening.start({mode:"continuous"})`，并确认响应 mode。每句结束继续收下一句；再次 QQ 关闭路由与连接，Python 必须停止采集/识别。旧 `speech.interrupt` 仅保留兼容。
3. 输入专用服务也保留 `speech.clear` 的空操作兼容。现有游戏在发消息/取消时会调用它，不能简单把所有 speech 方法都删掉。
4. `recognition.started` 不能拿来冒充 VAD“检测到人声”。目前游戏也没有接好的实时电平/人声活动事件；先独立展示，接入游戏前共同定义扩展。
5. 普通识别只发一次 `input.final`，包含 `input_id/text/language/intent`，事件信封带 `session_id/event_id/seq`。不要把部分文本、口令和最终文本重复发送成多条输入。
6. `intent:null` 进入已有聊天；固定 intent 由游戏检查。游戏按 `(session_id,input_id)` 去重，回执不授权自动重试旧控制。
7. 当前 C# 请求约 10 秒超时、心跳间隔约 5 秒。模型冷启动和权限等待不能长期堵住协议循环；改变加载/ready 流程需游戏端同步修改。
8. 断线/关闭输入后必须停止采集并清理未完成输入，重连只收新句，不重放旧口令。
9. A1 选择「语音→文字」，不点「试听」。ASR-only 服务不必声明 TTS；游戏端尚未完成按 features 禁用全部输出控件，这是游戏方的后续工作。

详细方法、状态字段和示例统一以[主 API 文档](语音模块-开发功能与API.md)为准，不再在多份文档维护相互不同的必填参数表。

## 5. 游戏负责人负责的对接工作

| 工作 | 已有基础 | 下一步 |
| --- | --- | --- |
| 模式与输入入口 | 文字/语音→文字/语音→语音；`SubmitExternal` | 本轮按语音→文字验收，保留文字输入 |
| WebSocket 与路由 | 握手、状态查询、心跳、重连、中文分片、去重、主线程会话检查 | 与语音组替换后的服务做兼容回归 |
| 文本与控制回执 | 已接聊天/intent，返回 accepted/rejected/ignored | 提示不适用或忙碌原因；不把 received/accepted 当成 AI 已回答 |
| 发声状态展示 | 目前只有收音/播放/错误状态 | 语音组提供可信活动数据后，共同定义事件并接 UI；当前尚无实时 VAD 指示 |
| 能力与错误界面 | hello 带 features，错误提示可保留 | 对 ASR-only 服务禁用无能力的播报功能；验证断设备/拒权限反馈 |
| AI 与游戏 | 已有模型、快照、上下文和动作权限 | 验收识别文字进聊天后是否只发起一次模型请求，AI 保持文字回复 |

## 6. 首轮验收表

测试记录至少包含日期、系统、Python/依赖版本、麦克风型号/输入设备、ASR 模型、触发方式、预期与实测。先用少量自编固定句建立可复现记录，不直接写“识别率达标”。

| 层级 | 操作 | 可接受的证据 |
| --- | --- | --- |
| A0 设备 | 列出并选择麦克风 | 设备名称/ID 与实际输入一致，权限/设备错误有原因 |
| A0 无声 | 安静等待约 10 秒 | 看到输入电平/底噪，不持续误报正在说话 |
| A0 发声 | 说 5 句短句，每句之间停顿 | 每次发声与结束有对应反馈；采样量、峰值/电平与人声判定分别记录 |
| A0 干扰 | 键盘操作、游戏音效或外放 | 记录误触发与使用环境，不能只靠“非零峰值”宣布通过 |
| A1 连续普通句 | QQ 开启后连续说「你好」「这手牌怎么打」，每句停顿 | 两句各进入聊天一次、AI 文字回复；不再按键或唤醒。忙时后续句排队，实际提交时读取游戏状态 |
| A1 固定口令 | 在允许的测试状态说「暂停」 | 只形成一次 intent，游戏有处理回执，未另发普通聊天 |
| A1 否定/提问 | 说「先别暂停」「暂停以后怎么办」 | intent 为 null，走聊天，不直接暂停 |
| A1 静默/关闭 | 开启后静默，再说一句；再次 QQ 关闭后继续说 | 静默不关闭持续模式、无空输入；关闭后停止采集，未提交句清空，不发送残留文本 |
| A1 重复/重连 | 重发同输入或断开后连接 | 不重复调用 AI/动作，不重放旧句，关闭后无残留收音 |

mock 文本输入只验证 I4 的协议与游戏路由；合成音频只验证解码样本。两者都不能代替 I1/I2 的真人设备证据。扬声器静音不应阻止 A0/A1；不为本轮验收修改系统音量。

分别记录“开始发声→活动反馈”“说完停顿→最终文字”“收到文字→模型回复”的耗时。首次联调记录实测，再协商数值阈值；旧单句诊断/兼容输入最长 15 秒；持续模式静默不因此结束。QQ 是开启/关闭持续会话，不再是每句重新激活。

## 7. 每次交付给游戏负责人的内容

- 任务分支与提交号，说明实现 I1–I6 中的哪几项，不另起一个无人能拉取的独立工程。
- 可直接运行的入口、依赖、模型获取方式与设备选择说明；复用 `voice/src/spire_voice/` 和 `scripts/voice_dev.py`。
- 无游戏的采集/发声诊断结果，以及有游戏的输入→文字回复结果，分开记录通过、失败、未测。
- 接口变更同时更新 `protocol/` 示例、主 API 和双方兼容检查；新增 VAD/部分结果事件先共同确认。
- 日常小步 commit/push，完成可验收功能再提 PR；不提交录音、模型、令牌、设备私有配置和构建产物。
