# 《杀戮尖塔 2》AI 陪玩搭子简版需求分析

## 1. 产品目标

开发一个《杀戮尖塔 2》AI 陪玩搭子。玩家选择铁甲战士后，AI 自动读取游戏状态，提供决策建议，也能全程代操作。搭子说话自然、有趣，会适当安慰玩家，玩家可以随时交流、暂停或接管。

## 2. 第一版范围

- 游戏模式：单人模式。
- 支持角色：铁甲战士。
- 目标平台：macOS 和 Windows，优先在 macOS 开发与验收。
- 大模型：聊天和策略判断可以调用在线大模型。
- 语音：优先采用免费、本地运行的方案，效果和资源占用需要在目标 Mac 上验证。

### 角色扩展原则

系统采用通用架构，第一版以铁甲战士完成适配与验收。后续扩展角色时，复用聊天、语音、状态读取、自动操作、暂停接管和战斗搜索框架，重点补充角色策略、特殊机制适配与测试。

| 模块 | 角色扩展时的工作 |
| --- | --- |
| 聊天、语音、暂停与接管 | 共用现有能力。 |
| 状态读取与自动操作 | 复用框架，补充角色特有资源、状态和交互选项。 |
| 卡牌、遗物、商店与特殊选择 | 复用决策流程，根据角色机制和当前卡组调整评价策略。 |
| 路线规划与药水使用 | 复用判断框架，根据角色当前的生存能力、资源和成长需求调整策略。 |
| 战斗求解 | 复用 CombatSolver 搜索框架，核验角色卡牌、资源和特殊机制的模拟正确性，并分别测试求解速度与方案质量。 |

Spire Buddy 和 STS2-Agent 可提供通用接入与决策基础；CombatSolver 可提供战斗搜索基础。已有通用能力不等于所有角色均已达到本项目要求，新增角色需要单独完成兼容性、策略效果和性能验收。

## 3. 功能需求

| 模块 | 第一版要求 |
| --- | --- |
| 游戏状态读取 | 自动获取角色、血量、金币、卡组、遗物、药水、地图、当前选项和战斗状态。 |
| 卡牌与遗物 | 根据当前卡组、资源和后续需求，建议选择或跳过，并简短说明原因。 |
| 商店 | 综合金币和卡组短板，决定购买、删牌或保留金币。 |
| 路线规划 | 结合血量、战斗能力和资源推荐路线，并随局势调整。 |
| 特殊选择 | 对开局祝福、每幕开始的特殊选择提供建议。 |
| 自动托管 | AI 可以连续完成游戏操作，无须逐步确认；玩家随时暂停、接管和改变策略。 |
| 战斗求解 | 使用 CombatSolver，在获胜前提下寻找受伤尽可能少的方案。 |
| 自主用药 | AI 自主决定用药时机，优先保留药水，在保命、避免大量战损或提高获胜机会时使用。 |
| 文字与语音 | 支持文字聊天、持续监听与唤醒词语音输入、语音播报，可打断、静音及关闭麦克风。 |
| 陪玩性格 | 幽默朋友型，适当接梗和安慰，支持安静、普通、话多三种模式。 |

## 4. 战斗求解要求

战斗开始后，系统争取在几秒内给出首个可行方案，随后继续优化。玩家可以设置最长等待时间，到时执行当前找到的最好方案。

如果超时仍未找到获胜路线，AI 根据搜索进展选择延长计算，或执行较好的局部方案，再根据新状态重新求解。界面和搭子必须说明方案的不确定性，不能将局部方案表述为已验证的整场获胜路线。

CombatSolver 使用预算受限的搜索，因此产品目标是限定时间内尽可能少受伤，不能承诺每场都得到全局最优解。几秒内返回方案属于性能目标，是否达标需要实测。

## 5. 交互要求

建议先给结论，再简短解释；玩家追问时展开。主动发言应结合局面，避免重复点评或频繁打断。

示例：

> “这张挺诱人，但咱们现在更缺防御。先补生存，活着才有输出。”

> “这波确实难顶，先别急，我看看后面能不能把血量救回来。”

暂停后停止提交新动作；玩家改变游戏状态后，旧计划失效。恢复托管时重新读取状态并决策。

语音交流支持打断当前播报。唤醒检测优先在本地完成，并提供麦克风开关和监听状态提示。

## 6. 技术方案与主要难点

基于本地项目的初步分析，计划按以下职责组织系统。已有能力的实际兼容性和整合效果仍需联调验证。

| 项目或组件 | 计划承担的职责 |
| --- | --- |
| Spire Buddy | 游戏内聊天、状态读取、局外决策和自动托管。 |
| CombatSolver | 战斗搜索、预计战损与战斗执行。 |
| STS2-Agent | 接口、决策日志和流程设计参考，按需复用。 |
| 在线大模型 | 对话、局外策略和建议解释。 |
| 本地语音组件 | 优先免费完成唤醒、语音识别和语音合成。 |

主要难点：

- 加快 CombatSolver 找到可用方案的速度，并评估速度与战损之间的取舍。
- 补齐搭子与求解器之间的接口，支持预算控制、结果读取和自然语言解释。
- 实现超时后延长计算或执行局部方案的判断机制。
- 验证 macOS 兼容性，并完成 Windows 适配与验收。
- 控制本地语音对游戏流畅度的影响。

## 7. 验收重点

| 验收项 | 验收要求 |
| --- | --- |
| 状态读取 | 能正确读取当前局面，决策使用最新状态。 |
| 决策建议 | 覆盖第一版需求中的各类选择，理由与当前局面一致。 |
| 自动操作 | 能连续完成操作，并根据执行反馈更新后续决策。 |
| 暂停与接管 | 暂停后不再提交新动作，接管后不执行过期计划。 |
| 战斗求解 | 遵循等待时间设置与超时处理规则，明确标注方案的不确定性。 |
| 语音交互 | 唤醒、识别、播报和打断可用，不明显干扰游戏。 |
| 陪玩体验 | 表达自然，幽默和安慰适度，三种发言模式有明确区别。 |
| 平台兼容 | 分别在 macOS 和 Windows 验证核心流程。 |

性能优化通过同一批战斗对比首条获胜路线耗时、最终战损和运行流畅度。

## 8. 待确定事项

- 目标 Mac 的芯片型号和内存容量。
- 战斗默认最长等待时间。
- 自动延长计算的次数或累计时间上限。
- 本地语音组件的具体选型，根据效果和性能测试确定。
