# 待办：决策策略化（规则/求解器优先，LLM 只解释）

状态：**未开始**（2026-10-28 记录）。本文件只记录方案与待确认问题，不代表其中任何一项已实现。

## 1. 问题

当前所有建议都走一遍大模型：把快照发给模型，让它"看着办"。带来三个问题：

- **成本**：每次提问都是一次完整请求，问得越多越贵；
- **不稳定**：同一局面两次回答可能不同，难以测试和回归；
- **质量上限低**：模型不知道当前版本的卡牌数值与流派协同，只能给泛泛建议。

而这几类决策其实**有明确依据**，不需要模型自由发挥：

| 决策 | 依据 | 谁来做 |
| --- | --- | --- |
| 战斗出牌 | CombatSolver 的最优路线 | 求解器（已接入） |
| 选牌 | 角色流派 + 当前卡组构成 + 费用曲线 | 规则引擎 |
| 遗物 | 角色、当前构筑、代价与收益 | 规则引擎 |
| 商店购买 | 金币预算、缺什么、删牌价值 | 规则引擎 |
| 休息点 | 血量、关键升级、下一层风险 | 规则引擎 |
| 地图路线 | 可达节点、资源与风险 | 规则引擎 + 少量启发式 |

大模型退到**解释层**：把规则/求解器的结论翻译成"为什么"，以及处理规则覆盖不到的边缘情况。

## 2. 目标架构

```text
GameReader 快照（已有）
   ├─ Room / 手牌 / 遗物 / 金币 / 血量
   ▼
DecisionEngine（Core 纯函数，无游戏依赖、可单测）
   ├─ 输入：快照 + 角色数据 + 流派权重
   └─ 输出：Recommendation { ActionId, Reason, Confidence, Score, Alternatives[] }
   ▼
界面显示（结构化：推荐 + 一句理由 + 备选）
   ▼
LLM（可选）：只在玩家追问“为什么”或规则无覆盖时调用
```

关键约束：

- 规则引擎**不联网、不调用模型**，毫秒级返回，可离线测试；
- 推荐必须是**游戏端能识别的动作 ID**，不是自由文本；
- LLM 不能推翻规则结论，只能解释或提示“这条超出规则覆盖”；
- 规则与数据随游戏版本走，不写死在代码里。

## 3. 分阶段任务

### D1 选牌策略（最高价值）

- 每个角色维护若干**玩法流**（如铁甲：力量、格挡/壁垒、消耗、狂怒流血等，具体以当前版本为准）；
- 识别当前流派：核心卡/遗物、已有卡组构成、前几个奖励的选择；
- 打分维度：流派契合、费用曲线、即时战力、稀有度、与现有遗物协同；
- 输出：推荐一张 + 一句理由 + 与“跳过”的比较。
- 数据：卡牌元数据（费用、类型、稀有度、关键词、流派标签）+ 流派权重表。

### D2 商店与遗物

- 商店：预算分配、缺什么补什么、删牌时机、药水容量；
- 遗物：代价与收益、与流派协同、当前血量能否承受；
- 输出同 D1，允许“这次不买/不换”。

### D3 休息点、事件与地图

- 休息点：回血 vs 升级，看血量和关键待升级牌；
- 事件：规则覆盖常见分支，未覆盖时交给 LLM 并明说；
- 地图：只比可达节点，精英/商店/篝火的取舍。

### D4 战斗建议转述

- 求解器给出路线后，把“第 N 回合：防御 → 打击 → 打击，预计战损 1”转成两三句中文；
- 不重新用模型算，只是转述 + 必要的风险说明。

### D5 评估与回归

- 固定样本：代表牌组/种子/楼层，记录推荐与理由；
- 金样例（golden cases）：每个流派若干局面，改动后必须一致或有意更新；
- 不承诺用胜率做 A/B：样本量太大、方差太高，早期以金样例 + 人工评审为主。

### 已实现（P3 第一步）

「可以执行」卡片已覆盖三类界面，全部只执行玩家点击：

| 界面 | 按钮 | 执行方式 |
| --- | --- | --- |
| 卡牌奖励 | 每张候选 + 「跳过」 | 卡牌节点 `Pressed` / 跳过按钮原生点击 |

## 5. 待你确认的问题

1. **规则数据谁维护**：卡牌元数据与流派权重是数据文件，游戏更新就要动。谁负责？
2. **流派判定标准**：靠核心卡/核心遗物判定，还是靠“前 N 张牌的选择历史”？出现半套力量半套格挡时怎么办？
3. **适用范围**：先只做铁甲战士，还是同时铺其他角色？其他角色是否有你熟悉的完整流派表？
4. **LLM 的边界**：规则给出结论后，还允不允许 LLM 说“我建议不按规则”？我倾向不允许，只在规则无覆盖时接管。
5. **建议还是执行**：这一版只显示推荐，还是也要点一下执行（选牌/购买）？执行要等求解器组的执行权契约。
6. **未知卡牌**：新版本/未收录卡牌出现时，回退到 LLM 并标注“未收录”，还是直接说不知道？
7. **个人信息**：玩家是否可能故意走非常规流派？规则是否要支持“按玩家声明的流派”覆盖自动判定？
8. **验收方式**：你能接受“金样例 + 你本人试玩判断”作为验收，还是必须给出量化指标？

## 6. 执行权与冲突（2026-10-28 已实现）

「让 AI 操作」最大的风险是**两套代码同时动游戏**，或者一个过期决定落在新状态上。当前规则：

| 规则 | 实现 |
| --- | --- |
| 战斗只归求解器 | `SolverBridge.Owned` 时自动操作直接跳过；点击接管会先关闭自动操作 |
| 每次界面只操作一次 | 按界面实例标识计数：退出再进入同一界面不会重复执行；商店因此不会自动买空 |
| 过期决定必须丢弃 | 决策携带当时的快照指纹，执行前重读；指纹不一致即丢弃 |
| 只接受合法选项 | 模型只能从 `options` 里的 id 选；`ChoiceParser` 拒绝任何不在列表里的值（含散文） |
| 暂停/接管优先 | 暂停会关闭自动操作、取消进行中的请求、停止已接管的求解器 |
| 手动点击不受影响 | 自动关闭后，卡片仍可手动点 |

### 已实现

- 新增 `ChoiceParser`：解析 `{"id":"..."}` 或裸 id，拒绝未知/散文，附带检查。
- 新增 `ChatClient.DecideAsync`：结构化选择请求，只回 id，不进入聊天历史。
- 面板「局外自动操作」开关：开启后对**奖励 / 休息点 / 商店 / 选牌界面**各自动执行一次；战斗不参与。
- 自动决策要求模型同时给出 30 字内理由，执行后在聊天里记一条「自动：我选了「X」，理由…」，并写入卡片状态行。
- 失败可见：非法回复自动重试一次，仍失败/超时则在聊天里说明并关闭自动操作；日志记录 `auto_invalid` / `auto_failed` / `auto_stop`。
- 自动决策请求**显式关闭思考**（`thinking: {"type":"disabled"}`）：实测同一提示词下思考从 1538 字符降为 0，正文正常返回；若服务端拒绝该参数（HTTP 400）则退回无参请求并把预算翻倍。
- 自动决策的输出预算与聊天一致（1000 token），模型侧回复失败重试一次；`finish_reason=length` 时提示改为“预算被思考占满”。
- 选牌候选先去重：同名牌按（名称, 费用/升级状态）合并，详情标注「共 N 张」，id 仍指向第一张真实卡；16 张实际只剩 9 项，减少上下文与误选。
- 开关状态持久化到 `user://spire-companion/window-state.json`，标题栏显示「自动：开/关」，重启后保持；文件损坏回退为关闭。
- **选牌界面**（锻造选卡、删牌选卡）：已读取 `NCardGridSelectionScreen` 的候选与提示，支持「选中 → 确认」两步；自动模式选完会自动确认。

## 7. 自动化实测问题（2026-10-28，来自实机反馈）

### S1 商店策略质量差（高）

实测：自动模式在商店**删了一张牌、又买了一张牌**，但组合明显不合理。当前只是"让模型从商品列表里挑一个"，没有任何预算与需求判断。

需要补的规则（优先级从高到低）：

- 金币预算：留多少钱给后续商店/删牌；低于阈值时只考虑关键补强；
- 删牌时机：优先诅咒/状态/基础打击防御，牌组薄时不乱删；
- 购买优先级：先补当前短板（输出/防御/过牌），遗物与药水按协同打分；
- 允许"什么都不买"，并把剩余金币纳入后续路线判断；
- 删牌服务打开选牌界面时，删哪张也要按同一套规则，而不是随手挑。

### S2 休息点空转（中）

实测：锻造用掉后休息点只剩「休息」，满血时自动仍然选了休息（有效但无意义）。缺少「离开/继续前进」这一动作，导致自动模式在无收益界面浪费一次操作。

需要：休息点暴露 `ProceedButton` 作为"离开"选项，并在无有效收益时选择它。

### S3 自动化整体仍需调优（中）

- 每个界面只操作一次的规则要保留，但"离开"应算独立动作；
- 商店买完是否继续买、买到什么程度，等 S1 规则落地后再定；
- 选牌（锻造/删牌）目前按单张评分，未考虑牌组已有张数与费用曲线。

### S4 事件（读取已修，执行已补）

实测报错：`CanonicalModelException: ... RoomFullOfCheese used in incorrect place`，读取可变事件模型时抛异常，导致**整个快照读取失败**。

修复：改为读取 `NEventRoom` 的选项按钮（与 Spire Buddy 一致），并对标题/描述/选项逐项兜底；读取失败时返回"事件（内容暂不可读）"而不是让面板整体报错。事件选项执行、地图选路、休息点/商店"离开/继续"已补上；事件多段对话会按选项变化继续决策。

### S5 药水替换策略（中）

实测：药水栏满时不换药水，只能放弃奖励。当前默认改为**替换最右侧那一瓶**（用户指定），先把流程走通。

需要优化的部分：按价值替换（低价值/低稀有度/已用过效果最差的），而不是位置最右；换之前把新旧药水对比说一句；药水栏只剩功能性药水时不替换。

### S6 多选牌与宝箱（2026-10-28 实测补充）

- 「移除两张牌」这类多选界面会停：已让模型额外返回 `ids` 排序列表，自动按顺序选到确认可用为止；模型只给一个候选时会在聊天里说明并停止，不再静默卡住。
- 宝箱房会停：已补读取（开箱按钮/遗物/离开）与执行。
- 奖励里多个金币项"识别不了"：日志显示其实已领第一个金币，随后选药水时因药水栏满抛错而卡住；药水替换接通后应消失。

### S7 多选牌（延后，已记录）

"一次移除两张/升级两张"的事件在实测中仍会停：模型很少主动返回 `ids` 排序列表。当前行为是只选一张后停止并在聊天说明。

延后处理，候选方案：
- 界面文本里解析"选 N 张"，由代码强制要求模型返回 N 个 id；
- 或者分多轮问模型（每次排除已选），成本更高但更稳；
- 需要实机拿到 `decision kind=Select` 的提示文案。
