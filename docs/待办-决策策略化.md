# 待办：决策策略化（规则/求解器优先，LLM 只解释）

状态：**未开始**（2026-10-28 记录）。本文件只记录方案与待确认问题，不代表其中任何一项已实现。

## 1. 问题

当前所有建议都走一遍大模型：把快照发给模型，让它"看着办"。带来三个问题：

- **成本**：每次提问都是一次完整请求，问得越多越贵；
- **不稳定**：同一局面两次回答可能不同，难以测试和回归；
- **质量上限低**：模型不知道当前版本的卡牌数值与流派协同，只能给泛泛建议。

而这几类决策其实**有明确依据**，不需要模型自由发挥：

| 决策 | 依据 | 谁来做 |
| --- | --- | --- |
| 战斗出牌 | CombatSolver 的最优路线 | 求解器（已接入） |
| 选牌 | 角色流派 + 当前卡组构成 + 费用曲线 | 规则引擎 |
| 遗物 | 角色、当前构筑、代价与收益 | 规则引擎 |
| 商店购买 | 金币预算、缺什么、删牌价值 | 规则引擎 |
| 休息点 | 血量、关键升级、下一层风险 | 规则引擎 |
| 地图路线 | 可达节点、资源与风险 | 规则引擎 + 少量启发式 |

大模型退到**解释层**：把规则/求解器的结论翻译成"为什么"，以及处理规则覆盖不到的边缘情况。

## 2. 目标架构

```text
GameReader 快照（已有）
   ├─ Room / 手牌 / 遗物 / 金币 / 血量
   ▼
DecisionEngine（Core 纯函数，无游戏依赖、可单测）
   ├─ 输入：快照 + 角色数据 + 流派权重
   └─ 输出：Recommendation { ActionId, Reason, Confidence, Score, Alternatives[] }
   ▼
界面显示（结构化：推荐 + 一句理由 + 备选）
   ▼
LLM（可选）：只在玩家追问“为什么”或规则无覆盖时调用
```

关键约束：

- 规则引擎**不联网、不调用模型**，毫秒级返回，可离线测试；
- 推荐必须是**游戏端能识别的动作 ID**，不是自由文本；
- LLM 不能推翻规则结论，只能解释或提示“这条超出规则覆盖”；
- 规则与数据随游戏版本走，不写死在代码里。

## 3. 分阶段任务

### D1 选牌策略（最高价值）

- 每个角色维护若干**玩法流**（如铁甲：力量、格挡/壁垒、消耗、狂怒流血等，具体以当前版本为准）；
- 识别当前流派：核心卡/遗物、已有卡组构成、前几个奖励的选择；
- 打分维度：流派契合、费用曲线、即时战力、稀有度、与现有遗物协同；
- 输出：推荐一张 + 一句理由 + 与“跳过”的比较。
- 数据：卡牌元数据（费用、类型、稀有度、关键词、流派标签）+ 流派权重表。

### D2 商店与遗物

- 商店：预算分配、缺什么补什么、删牌时机、药水容量；
- 遗物：代价与收益、与流派协同、当前血量能否承受；
- 输出同 D1，允许“这次不买/不换”。

### D3 休息点、事件与地图

- 休息点：回血 vs 升级，看血量和关键待升级牌；
- 事件：规则覆盖常见分支，未覆盖时交给 LLM 并明说；
- 地图：只比可达节点，精英/商店/篝火的取舍。

### D4 战斗建议转述

- 求解器给出路线后，把“第 N 回合：防御 → 打击 → 打击，预计战损 1”转成两三句中文；
- 不重新用模型算，只是转述 + 必要的风险说明。

### D5 评估与回归

- 固定样本：代表牌组/种子/楼层，记录推荐与理由；
- 金样例（golden cases）：每个流派若干局面，改动后必须一致或有意更新；
- 不承诺用胜率做 A/B：样本量太大、方差太高，早期以金样例 + 人工评审为主。

### 已实现（P3 第一步）

「可以执行」卡片已覆盖三类界面，全部只执行玩家点击：

| 界面 | 按钮 | 执行方式 |
| --- | --- | --- |
| 卡牌奖励 | 每张候选 + 「跳过」 | 卡牌节点 `Pressed` / 跳过按钮原生点击 |
| 休息点 | 每个可用选项 | 与按钮上的 `Option.OptionId` 匹配后点击 |
| 商店 | 每件商品（含价格、售罄/买不起置灰） | `OnTryPurchaseWrapper`，与游戏自身购买同一入口 |

规则引擎尚未接入，当前仍由模型给建议、玩家点击执行；删牌服务会打开选牌界面，由玩家继续手动选择。

## 5. 待你确认的问题

1. **规则数据谁维护**：卡牌元数据与流派权重是数据文件，游戏更新就要动。谁负责？
2. **流派判定标准**：靠核心卡/核心遗物判定，还是靠“前 N 张牌的选择历史”？出现半套力量半套格挡时怎么办？
3. **适用范围**：先只做铁甲战士，还是同时铺其他角色？其他角色是否有你熟悉的完整流派表？
4. **LLM 的边界**：规则给出结论后，还允不允许 LLM 说“我建议不按规则”？我倾向不允许，只在规则无覆盖时接管。
5. **建议还是执行**：这一版只显示推荐，还是也要点一下执行（选牌/购买）？执行要等求解器组的执行权契约。
6. **未知卡牌**：新版本/未收录卡牌出现时，回退到 LLM 并标注“未收录”，还是直接说不知道？
7. **个人信息**：玩家是否可能故意走非常规流派？规则是否要支持“按玩家声明的流派”覆盖自动判定？
8. **验收方式**：你能接受“金样例 + 你本人试玩判断”作为验收，还是必须给出量化指标？

## 6. 执行权与冲突（2026-10-28 已实现）

「让 AI 操作」最大的风险是**两套代码同时动游戏**，或者一个过期决定落在新状态上。当前规则：

| 规则 | 实现 |
| --- | --- |
| 战斗只归求解器 | `SolverBridge.Owned` 时自动操作直接跳过；点击接管会先关闭自动操作 |
| 每次界面只操作一次 | 同一界面类型只执行一次，避免商店自动买空；切换界面后重新计数 |
| 过期决定必须丢弃 | 决策携带当时的快照指纹，执行前重读；指纹不一致即丢弃 |
| 只接受合法选项 | 模型只能从 `options` 里的 id 选；`ChoiceParser` 拒绝任何不在列表里的值（含散文） |
| 暂停/接管优先 | 暂停会关闭自动操作、取消进行中的请求、停止已接管的求解器 |
| 手动点击不受影响 | 自动关闭后，卡片仍可手动点 |

### 已实现

- 新增 `ChoiceParser`：解析 `{"id":"..."}` 或裸 id，拒绝未知/散文，附带检查。
- 新增 `ChatClient.DecideAsync`：结构化选择请求，只回 id，不进入聊天历史。
- 面板「局外自动操作」开关：开启后对**奖励 / 休息点 / 商店**各自动执行一次；战斗不参与。
