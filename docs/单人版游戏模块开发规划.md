# 单人版游戏模块开发说明与规划

## 1. 目标和边界

依据 [单人版需求](AI陪玩搭子-简版需求分析.md)，开发一个能够读取游戏状态、提供建议并自动操作的铁甲战士 AI 陪玩 Mod。使用 C#、.NET 9 和游戏现有 Godot 接口；游戏端优先在 macOS 开发与验收，再完成 Windows 验证。

本阶段只做单人模式，不包含双开、联机、第二角色控制和多人 CombatSolver 适配。单人闭环稳定后，再按独立的双排需求扩展。

语音由另一组开发，语音模块优先 Windows。游戏组先通过文字和模拟语音服务完成验证，不把真实语音完成作为游戏开发的前置条件。旧单人需求中的语音 Mac 验证描述，以后来确定的语音 Windows 优先安排为准；整体仍需分别完成两平台联调。

本文是开发计划，不表示其中的新接口、模块和性能目标已经实现。具体排期需根据首轮兼容验证和人员投入确定。

## 2. 技术路线与现有代码复用

选择 Spire Buddy 作为单人产品主体，CombatSolver 作为战斗核心，STS2-Agent 按需参考，不同时启动两套自主操作循环。

| 项目 | 复用内容 | 本阶段需要做的工作 |
| --- | --- | --- |
| Spire Buddy | 游戏内聊天和设置、状态快照、合法动作、局外决策、模型客户端、停止和状态校验。 | 跑通当前版本；整理统一控制入口；补充策略、发言模式、语音通信及求解结果展示。 |
| CombatSolver | 战斗模拟、搜索预算、整场战损、药水策略、路线复用与自动执行。 | 验证 macOS；补充稳定桥接接口；测量短预算质量和耗时后优化。 |
| STS2-Agent | 场景处理、决策记录和动作接口设计。 | 遇到具体缺口时定向参考，不整体引入第二套自动游玩系统。 |
| game/legacy | 正式 C# 游戏主代码开发位置。 | 旧 Python 原型已清理，在此建立游戏主工程与对应测试。 |

可直接阅读的入口：

- [Spire Buddy 架构](../game/spire-buddy/docs/architecture.md)。
- [状态与动作绑定](../game/spire-buddy/mod/SpireBuddy/Game/GameBindings.State.cs)。
- [运行控制](../game/spire-buddy/mod/SpireBuddy/Runtime/BotRuntime.cs)。
- [当前 CombatSolver 桥接](../game/spire-buddy/mod/SpireBuddy/Game/CombatSolverBridge.cs)。
- [CombatSolver 说明](../game/CombatSolver/README.md)。

当前 Buddy 桥接主要支持探测可用性、查询全自动状态、启停接管和隐藏覆盖层，不能据此认定已有“读取最好路线、配置预算、导出战损”的完整集成接口。调用求解器内部反射成员需要锁版本并做能力检查，不能当作长期稳定的公开 API。

CombatSolver 的战前预测 API 文档注明仅支持 Windows。本阶段路线规划先使用可见地图、卡组、血量和资源，不依赖该接口，也不把战前预测的平台限制直接等同于普通战斗求解的平台限制。

## 3. 游戏端模块拆解

以下模块是建议的职责边界，可在现有代码上分步整理，不要求先大规模重写。

| 模块 | 输入与职责 | 输出或结果 |
| --- | --- | --- |
| 游戏适配 | 主线程读取角色、牌组、遗物、药水、地图、选项、战斗和当前可操作状态。 | 不可变快照、快照标识、合法动作。 |
| 运行控制 | 管理只建议、自动托管、暂停、错误和人工接管；处理状态变化。 | 当前控制状态和唯一动作执行权。 |
| 局外决策 | 卡牌、遗物、商店、删牌、路线、祝福、每幕特殊选择，以及正常流程需要的事件和休息点。 | 合法动作 ID、简短原因、必要的不确定性说明。 |
| 战斗桥接 | 提交当前战局、设置预算、观察进展、获取最好方案、停止和执行。 | 带状态标识的路线、战损和执行反馈。 |
| 动作执行 | 在执行前校验最新状态，调用游戏原生动作，等待结算。 | 成功、未执行、状态过期或结果不确定。 |
| 对话与性格 | 解释建议、响应玩家、生成适量幽默和安慰。 | 玩家可读文本及可选播报文本。 |
| 语音通信 | 接收文字和固定口令、提交播报、处理回执和重连。 | 转入统一输入入口，不直接绕过动作校验。 |
| 界面和日志 | 展示托管状态、求解状态、方案和错误，记录关键决策与耗时。 | 可操作面板和可定位问题的日志。 |

必须保持：只有一个控制器拥有实际动作执行权。战斗期间由 CombatSolver 执行，局外由 Buddy 执行；交接时停止另一方的动作提交，不能仅靠隐藏界面表示已停止。

## 4. 运行闭环与暂停规则

基本流程：读取稳定状态 → 判断场景 → 生成建议或搜索 → 检查快照和合法动作 → 执行一次 → 等待结算 → 刷新状态。

建议将状态分为：`Idle`、`Observing`、`Deciding`、`Searching`、`Executing`、`Paused`、`Error`；加载和动画期间等待，不将尚未可操作的界面当作决策输入。

关键规则：

1. 文字按钮和语音口令共用暂停、恢复与托管控制入口。
2. 暂停立即使当前控制版本失效、取消待处理请求，并阻止提交新动作。已经进入游戏结算的动作不强行回滚。
3. 旧模型响应和旧搜索结果即使稍后返回，也不能重新启动托管。
4. 玩家手动操作改变状态后，旧方案失效；第一版保守地暂停托管并提示，恢复时重新读取状态。后续再优化可继续复用的情况。
5. 动作执行结果不确定时，不自动重试同一购买、用药或出牌，先停下来核对状态，避免重复消耗。
6. 保存退出、读档和新开一局时，清理旧跑局的计划、任务和语音播报。

建议结果采用游戏端枚举的动作 ID，模型不直接生成可执行代码或任意命令。游戏对象读写放在主线程，模型请求和搜索在后台进行。

## 5. 局外决策怎么开发

先复用现有合法选项与模型调用，再逐个场景补充上下文、策略和测试。

| 场景 | 决策所需信息 | 验收重点 |
| --- | --- | --- |
| 卡牌奖励 | 当前牌组、费用结构、输出与防御短板、遗物、可选卡牌和跳过选项。 | 能选牌也能跳过；理由符合实际牌组。 |
| 遗物 | 候选效果、代价、当前资源和牌组协同。 | 不捏造效果，考虑负面代价。 |
| 商店与删牌 | 商品、价格、金币、可删卡牌、已有资源和后续需求。 | 不超预算；每次购买后重新读取库存和金币。 |
| 地图 | 可达节点、房间类型、血量、药水、牌组强度、Boss 与可见风险。 | 只选可达路线，受伤或资源变化后重新评价。 |
| 开局祝福、每幕选择 | 真实选项、成本、奖励和当前上下文。 | 通过实际界面验证每种流程，不把通用事件支持等同于全覆盖。 |
| 事件与休息点 | 当前选项、静态规则、血量和可升级牌。 | 支撑正常整局推进，不在未支持场景反复点击。 |

结论先行，默认一两句话说明。优先使用当前游戏数据和规则查询；信息不足时标明未知，不依赖模型记忆猜卡牌数值。

## 6. 战斗桥接接口规划

先封装统一适配层，以下名称是待实现的游戏端内部契约，不是已经存在的 CombatSolver API。类型与异步签名在实现时统一确定。

| 契约 | 职责 |
| --- | --- |
| `GetCapabilities` | 返回版本及是否支持进度、预算、局部路线、取消和执行等能力。 |
| `StartSearch` | 绑定跑局、战斗和根状态标识，提交时间、节点和药水策略。 |
| `GetProgress` | 获取已用时间、节点、当前最好结果及终止原因。 |
| `CancelSearch` | 取消搜索，并阻止其结果进入执行。 |
| `GetBestPlan` | 获取只读方案，区分已找到获胜路线、局部方案和无可用方案。 |
| `ExecutePlan` | 复核实际状态后执行可支持的一段动作。 |
| `StopExecution` | 停止后续动作提交，并报告已执行范围。 |

结果至少包含请求 ID、跑局与战斗标识、根状态标识、结果类型、预计战损、用药、动作摘要、已用预算、限制和错误。不依赖界面文字抓取来判断搜索结束。

单人版需求未规定排除求解器内部的 RNG 信息；应记录当前模拟依赖的可见和内部信息范围。不要将读取确定内部状态的结果描述为仅基于玩家可见信息的推理，也不要把双人版的信息限制默默套用到单人版。

## 7. 限时搜索和超时处理

产品目标是在几秒内争取提供首个可行方案，再利用剩余预算改进。具体秒数未确定，使用可配置项，不写死“必定几秒完成”。

处理顺序：

1. 在稳定玩家操作阶段启动短预算搜索并展示进度。
2. 获得获胜路线时展示“当前找到的最好方案”和预计战损，不能称为全局最优。
3. 达到用户等待上限后，停止或冻结该轮搜索，校验并执行已获得的适用方案。
4. 尚无获胜路线时，根据进展和硬预算选择延长一次或执行可用局部方案，执行后从新状态求解。
5. 延长次数和累计耗时设有限上限，不能无限延长。没有可验证的局部方案时暂停并提示，不强行出牌。

局部方案的读取与执行能力必须先验证；若当前求解器接口不支持，先补齐能力，该需求不能靠把失败搜索结果直接执行来实现。局部方案本身不保证最后能获胜，需要明确提示玩家。

药水优先保留，复用求解器智能用药与机会成本策略。界面允许查看本场用药理由；大模型不能在求解器执行时另行使用药水。战损与药水成本如何权衡需要用代表场景调试，不能仅用“总是省药”替代判断。

## 8. CombatSolver 加速计划

先测量再优化。固定游戏、Mod 版本、战斗样本和硬件，保存改动前基线，区分加载、捕获状态、模拟、搜索、GC 和执行动画耗时。

| 步骤 | 工作 | 判断依据 |
| --- | --- | --- |
| 基线 | 收集普通战斗、精英、Boss，以及抽牌、选牌、高分支和用药场景。 | 记录首条获胜路线时间、预算内战损、完成情况和峰值资源占用。 |
| 参数调优 | 比较短时间预算、Beam 宽度、节点预算和并行度。 | 同时看速度、战损和帧率，不只看 CPU 使用率。 |
| 路线复用 | 检查状态一致时能否沿用路线，减少无谓重算。 | 复用正确率、意外重算和执行偏差。 |
| 热点优化 | 定位重复模拟、状态复制、合并与分配开销。 | 只优化实际热点；剪枝和合并不能破坏状态语义。 |
| 回归 | 同条件重跑目标样本和不可退化的代表样本。 | 首解更快，同时不增加错误执行或明显恶化方案质量。 |

分别记录首个局部建议和首条完整获胜路线的时间，不能用前者证明后者达标。报告未找到获胜路线的比例和超时情况，不只统计成功样本；有条件时报告中位数与高分位耗时。

不要用新写的简化模拟器替换现有正确模拟来换速度，也不要把增加并行度当作所有电脑的通用加速方法。可见卡顿需要真实游戏验证，离线耗时不能替代帧率结论。

## 9. 对话、界面和语音接入

文字版先具备聊天、只建议/托管切换、暂停、恢复、求解进度、等待预算、结果与错误提示。建议解释依据真实选项和求解数据生成，不让模型编造预计伤害。

设置安静、普通、话多三档：分别侧重必要提示、关键点评、适量闲聊。将发言触发、去重、频率和性格文本分开管理，避免只修改一句提示词。战败或失误时简短安慰，不责备、不持续打断玩家。

游戏端作为语音 WebSocket 客户端，按 [语音 API](语音模块-开发功能与API.md) 实现握手、状态、固定口令、最终文本、播报提交、取消和回执。`input_id` 去重；断线后不重放旧口令，语音不可用时仍可文字操作。

战斗方案变化、暂停或退出时取消对应过期播报。语音打断只表示停止声音并收音，不应自动等同于暂停游戏；明确识别到暂停口令或点击游戏暂停按钮后，才调用游戏暂停入口。双排交接口令在本阶段不能误触发单人动作。

## 10. 开发阶段与交付门槛

按验收门槛推进，不先承诺固定周数。求解加速可以在基础接入稳定后与局外策略并行。

| 阶段 | 开发内容 | 完成标准 |
| --- | --- | --- |
| P0 环境和兼容基线 | 固定版本，在 Mac 构建加载 Buddy 与 CombatSolver，记录依赖和安装步骤。 | 进入铁甲战士战斗，可读状态、获得路线；明确平台不支持项和阻塞。 |
| P1 文字最小闭环 | 单一动作执行权、按钮控制、一次建议到一次执行，覆盖暂停和人工干预。 | 出牌与结算正确，暂停后旧任务不再动作，错误不重复执行。 |
| P2 战斗接管 | 桥接结果和预算、战斗内选牌、用药、跨回合续用和失败提示。 | 一场战斗可连续执行，状态偏离后正确失效或重算，结果可解释。 |
| P3 局外流程 | 奖励、商店、地图、祝福、每幕选择、事件和休息点。 | 各场景代表用例通过，能连续推进；未知场景停止而非乱点。 |
| P4 搜索优化 | 基线、参数实验、热点改进、限时与局部方案策略。 | 提供速度与战损对照；达到双方确认的指标或清楚记录未达项。 |
| P5 陪玩与语音 | 发言档位、性格、安慰、模拟通信及真实语音联调。 | 文字功能独立可用，语音口令不重复执行，断线不恢复旧动作。 |
| P6 双平台验收 | Windows 构建安装、Mac 回归、打包说明及整局验证。 | 两平台核心流程有记录；整局通关率、卡死率等按实际结果报告。 |

P0 未通过时先解决平台阻塞，不把未验证能力写成已完成。P6 的整局验证不等于承诺每局获胜。

## 12. 代码放置和上游提交

正式单人游戏主工程放在 `game/legacy/` 内，沿用该目录名但不再表示旧 Python 原型。以 Spire Buddy 的现有设计和能力作为主体复用基础，逐项确认采用依赖接口还是移植必要模块；移植时保留许可与来源，避免重复加载相同功能。确需上游修复时在其团队维护分支提交；求解器自身改动放在 `game/CombatSolver/`。不要把整个上游仓库复制进主工程，也不要同时运行多套动作控制器。工程结构在环境验证阶段确定。

`game/spire-buddy/`、`game/STS2-Agent/` 和 `game/CombatSolver/` 是子模块，`game/legacy/` 是主仓库直接管理的普通目录。修改上述子模块代码时，须先在对应团队可访问的 fork 建分支、提交并发布，再更新主仓库的子模块 URL 和提交指针；只在主仓库执行 commit 不会保存子模块内部未提交源码。主工程内的代码直接随主仓库提交，不需要子模块操作。保留许可证和来源信息。

本轮文档不建立 fork，也不改变子模块版本；正式开发开始前由负责人落实团队远端。操作流程参考 [Github代码提交指南](Github代码提交指南.md)。

## 13. 测试和验收安排

- 无游戏环境：测试策略数据整理、协议解析、去重、暂停竞态、超时状态机和模拟动作反馈。
- 有游戏环境：验证真实状态、目标、卡牌选项、用药、结算、人工接管和场景推进。
- 性能：同样本、同预算、同版本比较首解时间和战损，再在可见游戏中检查卡顿。
- 语音联调：先模拟服务，再按平台验证真实设备；不要求所有成员都运行游戏。

仓库已有基础检查：

```bash
python scripts/check_repository.py
```
