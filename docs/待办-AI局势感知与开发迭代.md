# 待办：AI 局势感知与开发迭代

状态：**未开始**（2026-10-27 记录）。本文件只列计划，不代表其中任何一项已经实现；完成后在对应条目补日期与验证依据。

## 1. 背景：Spire Buddy 怎么让 AI 看到局势

阅读 `game/spire-buddy` 源码后的结论，作为本项目的参考：

| 机制 | 位置 |
| --- | --- |
| 按界面类型分块快照，`state_type` 覆盖 event / map / card_reward / rewards / shop / hand_select / overlay 等 | `mod/SpireBuddy/Game/GameBindings.Snapshot.cs` |
| 每个界面独立读取函数（事件、商店、卡牌奖励、地图） | 同上，`BuildEventState` / `BuildShopState` / `BuildCardRewardState` / `BuildMapState` |
| 状态压成行式文本 + JSON 表格压缩，重复项合并 | `Runtime/GameState.Brief.cs`、`Runtime/CompactState.cs` |
| 首轮发全量，之后只发 JSON Pointer 差异；超预算重开 | `Runtime/AgentSession.cs` |
| 按界面定制提问模板（事件比分支、地图比路线、奖励比跳过） | `Runtime/JevContext.cs` |
| 合法动作带人话摘要、卡牌与目标预览 | `Runtime/JevContext.DescribeActions` |
| 只读查询工具：事件分支、敌人行动、卡牌文本、对局历史 | `Runtime/BotRuntime.cs` 工具列表 |

本项目当前只覆盖战斗字段与事件选项，奖励、商店、休息点、地图、卡牌文本、敌人意图都还没有接入，模型只能回答“看不到”。

### T2 按界面写提示词模板（高，改文本即可）——**已实现，待实机确认**

- 注意：未知信息必须明说，不得补全。

### T3 卡牌与遗物文本查询（中）——**手牌与候选已带文本**

2026-10-28：手牌、卡牌奖励候选、选牌候选都会附带卡牌描述（去掉 BBCode，截断到 100–140 字）；**牌组也已带描述**（截断 80 字），便于模型评估牌组协同。完整图鉴查询（按名称查任意卡/遗物）仍未做。

- 验收：对同一张牌，模型复述的效果与游戏内文本一致；查不到时明确说查不到。
- 风险：描述文本可能含 BBCode 或本地化标签，需要清洗后再发送。

## 3. 开发迭代：改代码就要重启游戏的问题

### 根本限制

Godot 导出的游戏只在启动时加载一次 Mod 程序集，C# 程序集在当前 .NET 运行时无法卸载再装入；游戏内没有"重新加载 Mod"的入口。**因此改 C# 代码必须重启游戏，这一点没有绕过的办法**，包括热重载工具：它们只在 Godot 编辑器里对编辑器会话有效，对已导出的游戏不生效。

可以直接降低摩擦的是下面三类，按投入从低到高：

### A. 一条命令完成构建、安装、启动（低）

- 现状：改完要手动 `build`、`install`，再切到 Steam 启动游戏。
- 做法：新增 `game_dev.py run`，串起 build → install → 启动游戏进程；失败时停在构建阶段不启动，保证不会用旧 DLL 掩盖错误。
- 收益：把四五步压成一条命令，但**仍需重启游戏**，只是不用手动点。
- 验收：改一行文案后，一条命令进入游戏看到变化。

### B. 把可变部分挪出 DLL：配置与提示词热加载（中）

- 做法：主题色、窗口尺寸、按钮文案、提示词模板放到 `user://spire-companion/ui.json` 与 `prompt.md`，模块启动时读取，并提供一个热键（如 F10）重新读取。
- 收益：调色、改文案、改提示词**不必重启**，只有改 C# 逻辑才需要。
- 注意：配置解析失败要回退到内置默认值并在状态栏提示，不能因为配置写错就白屏。
- 验收：游戏运行中改 `ui.json` 的颜色后按热键生效。

### C. 把"大脑"拆成独立本地服务（高，长期）

- 做法：Mod 只负责读取快照、展示界面、发送事件；提示词组装、模型调用、上下文管理、未来的局外决策放到本机独立进程（C# 控制台或 Python），通过 localhost WebSocket/HTTP 通信。这与项目既定的「C# 游戏端 + Python 语音端 + 协议」方向一致。
- 收益：调提示词、换模型、改决策逻辑只需重启服务（秒级），**改 DLL 的频率大幅下降**；服务还能单独做单元测试和回放。
- 代价：多一个进程要启动与守护；协议要定义清楚；游戏端断线要能降级为纯界面。
- 验收：服务重启后游戏内聊天自动重连，无需重启游戏。

### 建议顺序

先做 A（半小时内），解决"每次手动点四步"；再做 B（半天），把调样式与提示词的循环从"重启"变成"按热键"；C 放到 P2 之后，等决策逻辑真的复杂起来再拆，避免过早引入进程间通信。

## 4. 求解器体验与性能（2026-10-27 暂缓，先记录）

用户实测：原版 CombatSolver 0.50.1 已能接管战斗，但它的覆盖层窗口信息过载，玩家实际只需要「当前路线摘要 + 求解耗时」；另外卡组变多、楼层变深后搜索明显变慢。**本轮决定先不做**，记录方案备选。

### T7 求解器界面静默/折叠（中）

| 方案 | 做法 | 风险 | 维护 |
| --- | --- | --- | --- |
| A. 反射折叠 | 调用 `SolverOverlay.SetCollapsed(true)`，面板缩成小栏 | 低 | 无 fork，升级可能失效 |
| B. 强制隐藏 | 反射把覆盖层 `Visible=false` | 高：它内部多处用 `Visible` 判断刷新，可能导致路线停更 | 不建议 |
| C. 本地补丁静默模式 | 我们本来就从源码构建，加开关：不画面板、照常搜索执行，并暴露只读摘要 | 低 | 需维护本地分支，升级要 rebase |

摘要数据来源（已确认可反射读取）：`SolverController.CurrentResultForBugReport` → `SolverResult`（路线动作、预计战损），`IsSearching` / `FullAutoEnabled` / `HasRetainedRoute` 状态；耗时字段需实机核对。

建议先做 A，若仍碍事再做 C。

### T8 求解器性能（高成本，先基线）

已在 `game/CombatSolver/docs/performance/` 发现上游自带性能基建：`PERFORMANCE_FIXTURES.md`、`server-gc.md`、`veryhigh-dop16-20261001.md`、计划复用实验（3.726 倍）等。分层策略：

| 层 | 内容 | 难度 | 说明 |
| --- | --- | --- | --- |
| L0 配置 | 预算档位、并行 2–16、提前结束阈值、药水策略、路线复用 | 易 | 不改代码 |
| L1 使用方式 | 超时返回当前最好方案、显示进度、可停止 | 易 | 我们 Mod 侧实现 |
| L2 参数实验 | 用上游 fixture 做 beam/节点/并行的 A/B | 中 | 需留改动前后证据 |
| L3 算法/分配 | beam 保留策略、状态复制、调度、GC | 难 | 19 万行，正确性约束强，建议交上游 |

先做 L0+L1，再按基线数字决定是否进 L2；L3 原则上不动。
