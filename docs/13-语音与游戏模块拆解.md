## 1. 语音模块：当前要交付什么

### 1.1 目标与顺序

先能检测玩家发声，再把语音转成文字交给游戏，AI 保持文字回复。TTS 和唤醒词后续增强，不阻塞当前输入验收。旧版“先 TTS、不做 ASR”的顺序已被本节取代。

```text
A0：麦克风/权限/设备 → 音频采集 → 电平与发声开始/结束反馈
A1：QQ 开启持续监听 → 每句句末判断 → 中文 ASR → input.final；再次 QQ 关闭
    → 游戏聊天与 AI → 文字回复
A2：可靠的唤醒词检测 → 复用 A1
B：游戏提供回复文本 → 清洗/TTS/队列/播放（后续）
```

采到音频不等于检测到人声，检测到人声也不等于识别出文字。这三项分开验收；当前没有接好的实时 VAD 游戏事件，语音组先交独立诊断能力，再共同定义界面事件。

### 1.2 按代码边界分工

| 范围 | 语音组 | 游戏负责人 |
| --- | --- | --- |
| 输入 | 麦克风、权限、设备、采集、发声检测、切句、中文识别 | 收音按钮、模式切换、输入/错误显示 |
| 协议 | Python 本机服务、状态、输入事件、回执接收、异常清理 | C# 客户端、主线程路由、去重、回执发送 |
| 固定口令 | 完整匹配并输出可选 intent，不处理混合句关键词 | 判断当前状态与权限，允许时执行，否则拒绝/忽略 |
| AI 内容 | 不另建模型对话、人格或策略 | 模型、快照、上下文、人格、内容和发言时机 |
| 后续播报 | 纯文本清洗、TTS、播放调度、打断和回声处理 | 提供文本/优先级/有效期/取消时机，显示字幕 |

角色策略与求解器优化归另外两位策略同学；游戏内字幕/设置 UI 归游戏负责人。旧稿把这些工作固定分给某位语音或策略成员的表格不再作为当前安排。

### 1.3 两位语音成员的交付

建议一人侧重采集/发声/识别，另一人侧重服务/兼容/交付；具体由马、胡共同认领，本文不替他们确认个人任务。

- 第一交付：设备与权限诊断，能观察说话开始/结束、无声及底噪；不依赖 TTS、AI 回复或 ASR 成功。
- 第二交付：真实中文输入通过 WebSocket 进入游戏，AI 显示文字；普通句、否定句、固定口令、取消/超时、断线均有记录。
- 共同交付：可运行源码、依赖/模型获取方式、设备选择说明、测试报告及任务分支提交号。

复用 `voice/` 基本服务，不从零重复开发协议。当前游戏的 `speech.interrupt` 也用于无播报时开始收音；`speech.clear` 在输入阶段须保留为空操作兼容。详见[对接清单](语音模块-接口与参数分析.md)。

### 1.4 当前不要求的验收

本轮不要求 AI 实际出声、选择音色、云端 TTS、人格台词改写、播报期间唤醒或双开语音归属。不能用 mock 输入、合成音频、握手成功、非零峰值或播放器进程结束，代替真实人声输入验证。

## 2. 游戏模块：具体要实现哪些部分

### 2.1 总体数据流

```text
游戏状态
  -> State Adapter（标准化）
  -> 场景识别（战斗/奖励/商店/事件/地图）
  -> 决策模块（solver / 选牌 / 自动控制）
  -> 动作校验（合法/新鲜）
  -> 执行（游戏 API）
  -> UI/语音/日志
```

### 2.2 模块总表

| 编号 | 模块 | 要做什么 | 优先级 | 阶段 |
|---|---|---|---|---|
| G-01 | 游戏接入 | 读 `/state`、`/actions/available`；发 `/action` | P0 | A |
| G-02 | 状态适配 | 原始 JSON → 内部 `CombatState`/`RunState` | P0 | A |
| G-03 | 场景识别 | 战斗/奖励/商店/事件/地图/休息/宝箱 | P0 | A |
| G-04 | 合法动作 | 枚举手牌、目标、结束回合；索引校验 | P0 | A |
| G-05 | 战斗求解 | exact/beam/rollout；掉血/击杀线/备选 | P0 | A |
| G-06 | 抓牌评分 | top-1/top-3/skip；牌组协同/费用曲线 | P0 | A |
| G-07 | 建议展示 | 手牌索引、目标、预计掉血、理由 | P0 | A |
| G-08 | 自动打牌 | 循环执行、暂停/接管、失败恢复 | P1 | B |
| G-09 | 语音/字幕 | 语音策略、TTS、字幕 | P1 | B |
| G-10 | 双人 co-op | 第二角色、actor、地图投票、存档隔离 | P2 | C |
| G-11 | 配置/诊断 | Endpoint/Model/Key、连接测试、日志 | P0 | A |
| G-12 | 评估/回归 | fixture、benchmark、10 场实机 | P0 | 全程 |

### 2.3 P0：A 观战搭子（先做）

#### G-01 游戏接入

- 读取 `GET /state`
- 读取 `GET /actions/available`
- 发送 `POST /action`（只读阶段可不发）
- 错误处理：连接失败/游戏不在战斗/状态过期

**验收**：能稳定读到当前手牌/敌人/奖励。

#### G-02 状态适配

- 手牌：ID/名称/费用/可打出/目标
- 玩家：HP/格挡/能量/遗物/药水
- 敌人：HP/格挡/意图
- 牌堆：抽/弃/消耗
- 场景：战斗/奖励/商店/事件/地图

**验收**：字段和游戏内一致；未知卡牌有降级。

#### G-03 场景识别

- `monster/elite/boss` → 战斗
- `card_reward/rewards` → 选牌
- `shop/event/map/rest/treasure` → 对应建议
- 其他 → 显示“暂不支持”

**验收**：不把奖励界面当战斗。

#### G-04 合法动作

- 手牌索引
- 目标索引
- EndTurn
- 药水/其他（后续）

**验收**：建议动作 100% 在合法列表内。

#### G-05 战斗求解

- exact 当前回合穷举
- beam 对比
- rollout 2 回合诊断
- 输出：动作/目标/预计掉血/敌方 HP/击杀

**验收**：固定 fixture 结果稳定；延迟可接受。

#### G-06 抓牌评分

- 三选一排序
- skip
- 依据：卡牌强度、牌组协同、费用曲线、Act/Boss
- 输出 top-1 + 2–3 条理由

**验收**：理由引用具体卡牌/数值。

#### G-07 建议展示

- 手牌列表 `[0]…[4]`
- 推荐动作 + 索引 + 目标
- 备选 top-3
- 预计掉血/敌方 HP
- 理由/警告

**验收**：一屏能看懂；不要求用户读 JSON。

#### G-11 配置/诊断

- Endpoint/Base URL
- Model
- API Key
- 连接测试（含 tool calling）
- 日志/错误提示

**验收**：配置失败能说清原因。

#### G-12 评估/回归

- 固定战斗 fixture
- exact/beam/rollout 对比
- 10 场实机冒烟
- 非法动作/崩溃/延迟记录

**验收**：每次改动有回归结果。

### 2.4 P1：B 自动打牌/语音

#### G-08 自动打牌

- 开始/单步/暂停/继续/接管
- 战斗、奖励、商店、事件、地图、休息、宝箱
- 执行前校验快照
- 失败熔断/超时/预算
- 决策日志

**验收**：10 场不崩；非法动作 0；可随时停。

#### G-09 语音/字幕

见第 1 节。

### 2.5 P2：C AI 第二队友

#### G-10 双人 co-op

- 拉起第二实例/加入本地大厅
- AI 只操作自己的角色
- 地图投票/目标协同
- 团队聊天
- 暂停/继续/异常恢复
- 存档隔离/备份

**验收**：10 场 co-op 不坏档；不替人类出牌；可暂停。

### 2.6 本期不做什么

- 全角色全卡池
- 全自动通关
- 排行榜/成就
- 云端账号
- 声音克隆
- 自研游戏引擎/双实例底座
- 复杂 Mod 生态兼容（先支持最小集合）

## 3. 模块依赖与开发顺序

```text
G-01 接入
  -> G-02 状态
  -> G-03 场景
  -> G-04 合法动作
  -> G-05 战斗 / G-06 选牌
  -> G-07 展示
  -> G-08 自动 / G-09 语音
  -> G-10 双人
```

建议顺序：

1. G-01/02/03：先能读
2. G-04/05/06：先能算
3. G-07：先能看
4. G-08/09：再能打/能说
5. G-10：最后双人

> 不要先做 G-10：co-op 的坑最多，容易把前四步拖死。

## 5. 验收口径

### 语音

- 该说时能说，不该说时闭嘴
- 不朗读符号/动作 ID
- 可静音/打断
- 字幕一致
- 失败不阻塞游戏

### 游戏

- 建议合法
- 状态正确
- 选牌有理由
- 自动打可暂停
- 双人可停/不坏档

> 先保“合法 + 有用”，再保“像队友”，最后才保“双人”。
