# 竞品与方案调研：StS2 战斗 AI / Overlay / 求解器

> 调研时间：2026-10-22 12:29（Asia/Shanghai）
> 目的：在继续优化 SpirePilot 前，确认世界上已经有哪些做法、我们该学什么、不该重复造什么。
> 关联：[开发问题与解决方案](06-开发问题与解决方案.md)、[项目规划](02-项目规划.md)、[战斗建议 MVP](03-战斗建议MVP说明.md)

## 1. 结论先行

1. **StS2 已经有成熟的战斗求解器**：`CombatSolver` 已做到跨回合模拟、预算内 beam、overlay、自动执行，目标版本 0.111.0。我们再做一个“更强的全局最优 solver”不现实，也不应该是主要卖点。
2. **Overlay 是刚需**：`BoberInSpire`、`sts2-card-advisor` 都采用“mod 导出状态 + 外部/内嵌 overlay”的形态，说明玩家不想在终端看建议。
3. **跨回合比单回合重要**：`CombatSolver` 的核心不是当前回合 DFS，而是继续预测抽牌、洗牌、敌人行动、药水、遗物和后续资源；我们目前只做单回合 exact，必须补跨回合评估。
4. **“全局最优”不可承诺**：成熟项目也明确写“预算是上限，不承诺数学全局最优”。我们应统一使用“模型内/预算内最优”。
5. **我们的差异化**：透明理由、exact vs beam 对比、可复现实验、轻量本地运行；不是和 CombatSolver 比谁的搜索更强。

## 2. 主要竞品

### 2.1 CombatSolver（最直接竞品）

- 仓库：https://github.com/Torch1230/CombatSolver
- 形态：StS2 单机战斗求解器 mod，C#/.NET 9/Godot，带 overlay、执行本回合、全自动。
- 目标版本：StS2 `0.111.0`；依赖 RitsuLib；MIT。
- 核心能力：
  - 跨回合搜索：抽牌、洗牌、敌人行动、持续状态、药水、遗物、选牌。
  - 预算内 Beam Search：低 60s/60k 节点，中 120s/120k，高 180s/250k，极高 300s/500k；支持 2–16 路并行。
  - 路线快照：按回合展示出牌、目标、选牌、药水、结束回合。
  - 实机与预测分离：后台只操作独立模拟分支；实际状态偏离时重新搜索。
  - 原生选牌/动画保留；执行本回合/全自动；覆盖层透明度/主题。
  - 战斗前预测 API：在隔离 headless 进程中恢复跑局，评估目标战斗战损。
- 明确边界：展示“预算内最佳路线”，不承诺数学全局最优；只支持 Windows/单人（其 API 说明）。
- 对我们的启示：
  - 单回合 exact 只能作为校验器，不能作为最终产品形态。
  - 跨回合 lookahead + 预算/并行是必需的。
  - Overlay 应该是产品的一部分，不是附加项。
  - “实机根状态 → 独立模拟 → 路线快照”的架构值得抄。

### 2.1.1 Spire Buddy（视频里更可能是它）

- 仓库：https://github.com/xzmzm/spire-buddy
- Steam 创意工坊：https://steamcommunity.com/sharedfiles/filedetails/?id=3802091577
- 版本：`1.2.11`；许可：MIT。
- 形态：**自包含 C# Mod**，没有外部 companion 服务、浏览器 dashboard 或 helper 进程；模型客户端、聊天、设置、动作校验、静态敌人/事件规则都在进程内。
- 核心能力：
  - 游戏内 Chat/Settings 面板，人格预设 + 自定义人格，中英文跟随游戏语言；
  - 读取实时状态，动作先本地枚举/校验，再执行；
  - 支持 OpenAI-compatible Endpoint（base URL）；
  - 可选 **Jev decisions**（TypeSafe choice API），分别控制 strategy/combat；
  - 可选 **Combat Solver 集成**：把战斗交给 CombatSolver 全自动，失败时回退；
  - 本地 `jev_lethal` 检查：对部分攻击牌做确定性斩杀证明；
  - 用 ILSpy **进程内反编译** `sts2.dll`，查敌人/事件静态规则；
  - JSONL trace、上下文 rollover、信息防火墙（去 seed/RNG/未来抽牌）。
- 与 STS2-Agent 的关键差异：
  - Spire Buddy 是**单实例 in-process** 的 AI 助手/自动游玩；README 没有描述“本地双实例 AI 队友”能力；多人模式反而会禁用部分本地斩杀校验。
  - STS2-Agent 的强项是**双实例 co-op AI 队友 + 外部 API/MCP 接管**。
- 对我们的启示：
  - 如果目标只是“游戏内 AI 搭子/自动打”，Spire Buddy 的形态更轻、更完整；
  - 如果目标是“AI 控制第二个角色和我双排”，STS2-Agent 仍是更直接的底座；
  - Spire Buddy 的“人格 + Jev + CombatSolver + 进程内规则查询”值得借鉴。

### 2.2 BoberInSpire（Overlay 架构参考）

- 仓库：https://github.com/S0ul3r/BoberInSpire
- 形态：C# mod 导出战斗/商店 JSON + Python 分析 + React/Tauri 半透明置顶窗口。
- 功能：伤害/格挡汇总、遗物摘要、卡牌奖励建议（Mobalytics tier + 牌组启发式）、设置面板/透明度。
- 对我们的启示：
  - Phase A 可以用“外部置顶窗口 + 本地 state API”，不必一开始做游戏内 mod overlay。
  - 状态/建议/UI 分层：mod 只导出，Python 决策，UI 只渲染。
  - 卡牌奖励推荐需要 tier/牌组数据；我们后续可接 Spire Codex 数据。
- 注意：它主要是 Windows 安装器/Tauri；macOS 需要自己搭 UI。

### 2.3 sts2-card-advisor（游戏内奖励 Overlay）

- 仓库：https://github.com/ing-gom/sts2-card-advisor
- 形态：StS2 mod，在卡牌奖励界面给每张卡叠加 tier、协同分、理由标签、skip 建议。
- 我们的启示：
  - 选牌推荐的“游戏内展示”已有验证；后续我们的选牌模块应直接做 overlay，而不是终端。
  - skip 建议是用户明确需求，必须建模。

### 2.4 cvennevik/slay-the-spire-solver（早期思路）

- 仓库：https://github.com/cvennevik/slay-the-spire-solver
- 形态：StS1 规则引擎 + 搜索，目标“最大化战斗结束 HP”。
- 作者明确说：全状态穷举大概率不可行，规则引擎本身是最大工作。
- 对我们的启示：
  - 不要低估规则引擎；我们目前只覆盖 Ironclad 子集。
  - 目标函数用“战斗结束 HP/战损”是合理起点，但要补充胜利约束与资源。

### 2.5 STS2MCP / SpireBench / AgenticSTS

- `STS2MCP`：我们当前的状态/动作源，HTTP 15526；提供完整战斗/菜单/奖励状态。
- `SpireBench`、`AgenticSTS`：LLM 长程评测；说明高难度下 LLM 仍明显落后专家，战斗是主要瓶颈。
- 对我们的启示：LLM 适合解释/长程先验，不适合替代战术搜索；我们的混合路线成立。

## 4. 我们应该怎么做

### 4.1 不重复造“更强 solver”

- 不与 CombatSolver 正面比搜索强度；它是成熟 C# 实现、跨回合、预算大。
- 我们做**轻量、可解释、可复现**的 copilot：适合研究、教学、二次开发。
- 如果用户只想要“最强自动打”，直接推荐 CombatSolver 更合理；我们的价值是“为什么”和“对比”。

### 4.2 先补跨回合评估，而不是继续堆单回合 DFS

- 当前 exact 只在单回合内最优；它会把“这回合少掉 3 血”误当成全局更优。
- 下一步实现 **rollout / 2–3 回合 lookahead**：
  - 叶子节点不直接评价，而是用贪心/beam 策略继续打到 2–3 回合，估计最终 HP/战损。
  - 抽牌仍然 sampling；报告“样本内期望”。
- 整场战斗仍用预算 beam，不做 BFS。

### 4.3 Overlay 分两阶段

- **Phase A**：外部置顶窗口（Tkinter/Tauri/Web），轮询 15526，显示 exact vs beam、手牌索引、预计掉血、击杀线。
- **Phase B**：游戏内 mod overlay（BaseLib/Godot），需要 C# 与游戏内 UI；等算法稳定后再做。

### 4.4 评估优先

- 固定 20–50 个战斗状态，比较 exact/beam/rollout 的：
  - 胜率/战损
  - 决策延迟
  - 与 exact 的动作一致率
  - 解释忠实性
- 没有评估，不要继续调权重。

## 5. 风险与合规

- CombatSolver 等竞品是 MIT，但各自依赖/资源许可不同；只参考思路，不复制代码/资源。
- 我们的数据来自 Spire Codex API；游戏内容归 Mega Crit。
- 自动执行只本地单机，不碰排行榜/成就。
- 不承诺“全局最优”；统一写“模型内/预算内最优”。

## 6. 本项目当前进展（2026-10-22 12:29）

- 已实现 `spirepilot overlay`：Tkinter 置顶窗口，轮询 STS2MCP 15526，显示手牌、exact 推荐、beam 对比、预计 HP/敌 HP/掉血。
- 已实现 `spirepilot live --solver exact|beam|compare`。
- 已做 15 个固定状态的 exact vs beam 基准：13/15 动作相同；2 个动作不同但 HP/掉血相同；小样本上 exact 未表现出战损优势。
- 结论：下一步优先跨回合 rollout + overlay 可用性，而不是继续加大单回合 DFS。
- 已实现 `spirepilot rollout`：2 回合 rollout 诊断；在 fixture 上，防御线 HP 70、结束回合线 HP 65，说明短视评估能区分“当前回合好/下一回合差”。
- 15 状态三路基准中 rollout 未优于 exact 首选（0/15），说明当前状态集/策略不足以证明跨回合收益；需要更多真实战斗。
