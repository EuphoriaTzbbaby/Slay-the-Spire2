## 2. 重大问题与解决

### ISS-001：把 StS1 的工具链套到 StS2 上

- **时间**：2026-10-21 22:33
- **现象**：初始分析引用 `CommunicationMod`、`spirecomm`、`slay-the-spire-mcp`，这些都是一代工具。
- **根因**：项目对象是 **Slay the Spire 2**，但早期调研沿用了 StS1 的生态记忆。
- **影响**：如果直接按 StS1 方案做，环境接入会完全走错。
- **解决**：
  - 改为 StS2 的 **`Communication_Mod_STS2` + BaseLib + Harmony**。
  - 删除开题里的 StS1 附录、[13]–[15] 工具参考。
  - README 增加「项目对象：Slay the Spire 2（StS2 EA）」。
- **验证**：全仓库无 `Sprie` 拼写；无 StS1 实现分支；41 个测试通过。
- **状态**：已解决。

### ISS-002：开发机没有安装 StS2 / Steam

- **时间**：2026-10-22 09:27
- **现象**：检查常见 Steam/游戏目录均为空，无法执行真实抓包。
- **根因**：当前环境只有项目代码，没有游戏运行环境。
- **影响**：D1–D3 真实联调无法在本机完成；只能做合成状态验证。
- **解决**：
  - 先实现 `capture` / `inspect` / `trace` 工具链，等游戏环境可用时执行。
  - 增加 `combat_minimal.json`，模拟真实上游缺字段的形态。
  - 所有文档明确标注「合成状态验证，不是真实游戏结论」。
- **验证**：capture/inspect/trace 均有测试；真实游戏仍未验证。
- **状态**：未解决（依赖用户环境）。

### ISS-003：macOS AirPlay Receiver 占用 5000 端口

- **时间**：2026-10-22 10:08
- **现象**：`lsof -nP -iTCP:5000 -sTCP:LISTEN` 显示 `ControlCe` 监听 `*:5000`，`make capture` 无法绑定。
- **根因**：macOS ControlCenter 的 **隔空播放接收器（AirPlay Receiver）** 默认使用 5000。
- **影响**：capture 起不来，游戏 mod 也连不上。
- **解决**：
  - 系统设置 → 通用 → 隔空投送与接力 → 关闭「隔空播放接收器」。
  - 重新 `lsof` 确认无输出。
  - 不直接 kill ControlCenter（可能自动重启，也影响 AirPlay）。
- **验证**：2026-10-22 10:11 用户关闭后 `lsof` 无输出；端口释放。
- **状态**：已解决。

### ISS-004：`make capture` 的会话路径与文档不一致

- **时间**：2026-10-22 09:59
- **现象**：文档写 `data/replays/d1/states.jsonl`，但 `make capture` 默认用时间戳会话。
- **根因**：Makefile 没有设置默认 `SESSION`。
- **影响**：用户按文档找不到文件；inspect 路径对不上。
- **解决**：Makefile 增加 `SESSION ?= d1`，`make capture` 固定写 `data/replays/d1/`。
- **验证**：`make -n capture` 输出 `--session d1`。
- **状态**：已解决。

### ISS-005：终端中文文件名显示成 `?`

- **时间**：2026-10-22 10:12
- **现象**：`ls docs` 显示 `01-????????????.md`，但文件实际存在。
- **根因**：终端 locale 不是 UTF-8（`LANG` 为空 / `LC_CTYPE=C`），或 Terminal 编码不是 Unicode。
- **影响**：看起来像文件损坏，容易误删/误改名。
- **解决**：
  - 临时：`export LANG=zh_CN.UTF-8; export LC_CTYPE=zh_CN.UTF-8`。
  - 永久：写入 `~/.zshrc`，并清理冲突的 `LANG=C`/`LC_ALL=C`。
  - Terminal 描述文件编码设为 Unicode (UTF-8)。
- **验证**：2026-10-22 10:15 `locale charmap` 输出 `UTF-8`，`ls docs` 正常显示 5 个中文文件名。
- **状态**：已解决。

### ISS-006：macOS 上 mod 是否加载尚未验证

- **根因**：缺少游戏环境；macOS 的 mod 支持可能受版本/路径/权限影响。
- **影响**：如果 macOS 不加载，D1 会直接失败。

- **状态**：未解决（待 S1 实测）。

### ISS-007：上游状态缺 `Block`、手牌费用/可打出等字段

- **时间**：2026-10-21 22:33（源码审计）
- **现象**：`MainFile.cs` 的 `Player` 没有 `Block`；手牌只有 `Card_Name`/`Card_ID`；敌人没有 `Block`。
- **根因**：mod 导出的是「够用就好」的子集，不是完整战斗状态。
- **影响**：攻防估值偏差；条件卡可能误判；斩杀线不准。
- **解决**：
  - 解析器缺字段时按 0/基础值估算，并输出 warning。
  - `inspect` 明确报告 `Player.Block`、手牌 `Cost/CanPlay`、敌人 `Block`。
  - `CardCatalog` 覆盖费用/伤害/格挡/目标。
  - 文档给出本地扩展 scanner 的字段位置与影子状态降级方案。
- **验证**：`combat_minimal.json` 缺 Block 时仍能给出建议，并带警告。
- **状态**：已缓解；根治需真实接入后补字段。

### ISS-008：`Card_ID` 是运行时 hash，不能当稳定主键

- **时间**：2026-10-21 22:33
- **现象**：`Piles` 里 `Card_ID = k.GetHashCode()`。
- **根因**：.NET 对象 hash 不稳定，跨局/跨版本不可复用。
- **影响**：回放、升级牌关联、卡牌去重会错。
- **解决**：持久化使用 `card_id + upgraded + pile + position`；动作只用当前手牌索引。
- **验证**：adapter 测试覆盖 `Card_Name` 与索引；回放不使用 hash。
- **状态**：已解决。

### ISS-009：每次出牌后手牌索引变化

- **时间**：2026-10-21 22:54
- **现象**：一次回多个动作会打到错误的牌；缓存的 `HandIndex` 会失效。
- **根因**：mod 每次状态变化都会重排 `HandPile`。
- **影响**：自动模式可能连续打错牌。
- **解决**：
  - **一次状态只回一个动作**。
  - 每次从最新状态重算索引。
  - 用 `(TurnNumber, ActionCount)` 去重，避免重复执行。
- **验证**：bridge 测试覆盖 copilot/auto；规划文档写明集成约定。
- **状态**：已解决。

### ISS-010：HTTP 响应体不是动作时，游戏会解析失败

- **时间**：2026-10-21 22:33
- **现象**：上游示例 `server.py` 返回 `{"status":"OK"}`，游戏会把它当命令解析。
- **根因**：游戏把非空且不等于 `OK` 的响应体直接交给 `ExecuteAICommand`。
- **影响**：日志报错；严重时动作不执行。
- **解决**：
  - copilot 模式返回精确的 `OK`。
  - auto 模式直接返回 `{"Type":"PlayCard",...}` 或 `{"Type":"EndTurn"}`，不包 `status`。
  - 文档写明响应体约定。
- **验证**：bridge 的 copilot/auto 测试通过。
- **状态**：已解决。

### ISS-011：卡牌数据不能直接套 StS1，且 StS2 数据需要重建

- **时间**：2026-10-21 22:54
- **现象**：项目初期没有 StS2 卡牌库；StS1 卡表与 StS2 差异很大。
- **根因**：StS2 是续作，卡池/数值/机制都变了。
- **影响**：用错卡表会导致费用、伤害、目标全错。
- **解决**：
  - 从 Spire Codex 公共 API 导入 87 张 Ironclad 机械字段。
  - 未知卡用实时 `CardCatalog` 回退。
  - 数据文件标注来源与版本；不包含图片/游戏资源。
- **验证**：`data/cards/ironclad_cards.json` 87 张；卡牌库测试通过。
- **状态**：已解决（机械字段）；复杂效果仍待补。

### ISS-013：`CardCatalog` 可能缺失或字段不全

- **时间**：2026-10-21 22:54
- **现象**：非 `OnTurnStarted` 触发可能没有 `CardCatalog`；部分卡只有名字。
- **根因**：mod 只在部分触发点发送 catalog。
- **影响**：升级牌/补丁数值可能按基础值。
- **解决**：
  - 静态库 + 实时 catalog 合并：实时字段优先。
  - catalog 缺失时回退静态库并 warning。
  - 卡牌 ID 别名（STRIKE → STRIKE_IRONCLAD 等）。
- **验证**：`test_missing_catalog_uses_static_db`、`test_catalog_fallback` 通过。

### ISS-014：敌人 `Index` 与列表位置可能不一致

- **时间**：2026-10-21 22:54
- **现象**：导出用 `Monster != null` 过滤敌人，命令执行器按 `CombatState.Enemies` 索引。
- **根因**：导出索引与执行索引不是同一套过滤逻辑。
- **影响**：`TargetIndex` 可能打错目标。
- **解决**：`inspect` 检查索引是否连续；bridge 以导出列表顺序为准；真实接入时验证。
- **状态**：待真实游戏验证。

### ISS-015：没有公开、可复用的 StS2 战斗模拟器

- **时间**：2026-10-21 22:54
- **现象**：无法像开源棋类那样直接 MCTS；游戏内动作不可逆。
- **根因**：StS2 是商业游戏，缺少公开模拟器/规则引擎。
- **影响**：搜索必须依赖自建前向模型，精度受限。
- **解决**：
  - 自建 `rules.py`：直接伤害/格挡/抽牌/能量/状态 + 部分能力。
  - 未覆盖效果按估值处理，并统一输出「近似建议」警告。
  - 用 golden trace 逐步对拍，而不是声称完全一致。
- **验证**：合成 trace 通过；真实 trace 待数据。
- **状态**：已缓解；保真度仍是最大风险。

### ISS-016：根动作评分被深层「结束回合」污染

- **时间**：2026-10-21 23:14
- **现象**：备选里的「结束回合」可能显示的是「先打几张牌再结束」的分数。
- **根因**：搜索在深层也会调用 `record_root(EndTurn)`，覆盖根动作分数。
- **解决**：只在 depth 0 记录根动作；深层用 `first_key` 更新对应根动作的最好分数。
- **验证**：搜索/备选测试；零能量时只返回 EndTurn。
- **状态**：已解决。

### ISS-017：推荐连招/理由与搜索采样不一致

- **时间**：2026-10-21 23:14
- **现象**：搜索在某个抽牌样本下选出的连招，复算时用了另一个抽牌顺序，理由里的卡名/伤害对不上。
- **根因**：`search` 返回动作序列但没有返回采样索引；`advisor` 用固定 RNG 复算。
- **解决**：
  - `SearchResult.sample` 记录样本索引。
  - `sample_state(state, sample)` 复现同一抽牌顺序。
  - `advisor._replay_sequence` 用同一 RNG 复算整条连招。
- **验证**：示例理由里的总伤害/剩余血量与连招一致。
- **状态**：已解决。

### ISS-018：理由只分析第一步，不分析整条连招

- **时间**：2026-10-21 23:20
- **现象**：推荐 Thunderclap 后，理由只说第一步 10 点伤害，没有说整条连招 43 点、击杀 Louse。

- **验证**：示例输出包含「整条连招合计约 43 点伤害」「连招内击杀 Louse」。
- **状态**：已解决。

### ISS-022：推荐动作与显示标签不一致

- **时间**：2026-10-22 12:13
- **现象**：显示「推荐防御」，但 `hand_index=0` 实际是打击；连招也从防御开始。
- **根因**：搜索聚合时 `best_action` 从 `root_actions` 取，而 `labels/sequence` 来自另一个样本的最佳线路；当根动作的最高均值线路与整体最佳线路不同，二者错位。
- **影响**：按索引打牌会打错牌，属于严重交互 bug。
- **解决**：
  - 始终用 `chosen.sequence[0]` 作为返回动作。
  - 如果 chosen key 与 best_key 不同，更新 best_key，保证 action/label/sequence 同源。
  - 增加回归断言：`advice.sequence[0] == advice.action`。
- **验证**：live 实测动作与手牌索引一致；44 个测试通过。
- **状态**：已解决。

### ISS-023：建议只在终端显示，缺少游戏内对比界面

- **时间**：2026-10-22 12:17
- **现象**：用户必须在终端敲 `make live`，无法在游戏画面上直接看到「推荐 vs 备选」。
- **根因**：当前只有 CLI + API，没有 overlay/UI。
- **影响**：操作割裂，无法边看牌边看建议。
- **解决方向**：
  1. **Phase A（快）**：本地置顶透明窗口/仪表盘，轮询 STS2MCP 15526，显示推荐、备选、理由；不改游戏。
  2. **Phase B（最终）**：BaseLib/Godot overlay mod，在游戏内画推荐标记；Python 只提供决策 API。
  3. 也可在 STS2MCP 的 UI 扩展中加一个 `/advice` 面板，但需维护第三方 fork。
- **进展**：2026-10-22 12:29 已实现 Phase A `spirepilot overlay`（Tkinter 置顶窗口，轮询 15526，显示 exact/beam 对比）。
- **状态**：已缓解（Phase A 完成；Phase B 游戏内 overlay 未做）。

### ISS-024：「最少受伤 + 击倒」的目标定义与 BFS/DFS 可行性

- **时间**：2026-10-22 12:17
- **现象**：用户希望「当场战斗的最优解：受伤最少且击倒敌人」，并建议 BFS/DFS。
- **根因**：目标函数未形式化；完整战斗搜索空间大，且抽牌顺序隐藏。
- **影响**：如果不定义优先级，搜索会给出互相矛盾的结果；如果直接全战斗 BFS，可能爆炸/无法保证。
- **解决/设计**：
  - 目标改为字典序：**先保证存活/击倒，再最小化实际掉血，再最小化回合/资源**；无胜利线时最大化存活概率/剩余 HP。
  - 当前回合已实现**穷举 DFS**（`src/spirepilot/exact.py`），深度 2–6 张牌，能做到「固定抽牌样本内的模型最优」。
  - 已加 `--solver exact|beam|compare`，可对比两者动作/掉血/敌方剩余 HP。
  - 整场战斗仍建议 **DFS + 记忆化 + 分支限界/IDA\***，不用 BFS；全战斗最优仍开放。
  - 抽牌未知时只能做「固定抽样下的最优」或「信念空间期望最优」；不能承诺真实游戏全局最优。
- **状态**：已缓解（exact-turn 已实现；全战斗最优仍开放）。

### ISS-025：「训练模型」的表述容易误解

- **时间**：2026-10-22 12:17
- **现象**：用户问「你是怎样训练模型然后给出连招建议」。
- **根因**：文档把「前向模型」和「机器学习模型」混在一起说。
- **事实**：
  - 当前**没有训练任何模型**。
  - 「模型」指手写规则的前向模拟器（伤害/格挡/抽牌/能量）。
  - 评分函数权重是手调的；搜索是 beam search。
  - 还没有用专家数据做监督学习、也没有 RL。
- **后续可选**：CEM/随机搜索调权重；专家轨迹做 learning-to-rank；更多数据后再考虑 RL。
- **状态**：已澄清（文档需继续避免「训练模型」歧义）。

### ISS-026：竞品 CombatSolver 已很成熟，定位需要调整

- **时间**：2026-10-22 12:29
- **现象**：调研发现 `CombatSolver` 已支持 StS2 0.111.0、跨回合模拟、预算 beam、overlay、自动执行，功能和完成度都高于我们当前版本。
- **影响**：如果继续以“更强 solver”为目标，投入产出比很差，而且容易重复造轮子。
- **决策**：
  - 不正面竞争搜索强度；我们的差异化为**可解释理由、exact vs beam 对比、可复现实验、轻量本地 copilot**。
  - 学习它的“实机根状态 → 独立模拟 → 路线快照”架构；后续补跨回合 rollout。
  - 如果用户只想要“最强自动打”，应直接推荐 CombatSolver，而不是硬做。
- **状态**：已缓解（定位调整；跨回合能力仍待补）。

### ISS-027：AI 双排需求与现有单机 copilot 架构不匹配

- **时间**：2026-10-22 17:59
- **现象**：用户希望 AI 像真人队友一样双排：知道手牌、给选牌/出牌建议、会吐槽/语音，最好还能控制自己的角色。当前项目只有单机状态读取、终端/置顶建议，没有双实例、动作执行、人格/语音层。
- **根因**：产品目标从“单机战斗 copilot”扩展到“游戏内具身协作 Agent”，需要新的接入、编排和交互层。
- **影响**：如果继续只优化单机 solver，无法满足“AI 队友”体验；如果从零做双实例/overlay，工作量过大。
- **决策**：
  - 新规划见 [AI 双排规划与难点分析](08-AI双排规划与难点分析.md)。
  - 分 A（观战搭子）→ B（双排参谋）→ C（AI 队友）三阶段；MVP 先做 A。
  - 不重复造双实例/overlay 底座；优先复用/评估 STS2-Agent 等现有实现。
  - 战术用 solver 保底，LLM 只负责解释/对话/人格。
- **状态**：已缓解（方向与阶段已定义；尚未实现）。

## 5. 经验与预防清单

1. **先锁对象再选工具**：StS2 就用 `Communication_Mod_STS2`，不要从 StS1 生态里猜。
2. **先审计字段，再写算法**：没有 `Block`/费用/可打出，solver 再强也不可信。
3. **一次状态只回一个动作**：手牌索引会变，缓存索引必出问题。
4. **缺失字段要显式警告**：宁可显示 `degraded`，不要假装 `ready`。
5. **搜索必须可复现**：记录抽牌样本；复算理由要用同一 RNG。
6. **根动作评分与深层评分分开**：不要把「先打牌再结束」的分数记到「立即结束」上。
7. **日志按工作块即时写**：开始/结束各一条，带 `YYYY-MM-DD HH:MM`。
8. **端口冲突先查 `lsof`**：macOS 的 AirPlay Receiver 会占 5000。
9. **终端乱码先查 locale**：`locale charmap` 不是 UTF-8 就修，不要重命名文件。
10. **文档路径不要带目录拼写**：用 `<项目根目录>`，项目名统一 Slay the Spire 2。
